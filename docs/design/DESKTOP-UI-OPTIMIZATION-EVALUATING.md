# CC Pocket 桌面端 UI 优化方向

状态：评估中，作为下一轮设计的输入，尚未冻结视觉规格或进入产品实现。

整理日期：2026-09-08（America/Los_Angeles）。

## 1. 要解决什么问题

用户对两张桌面截图的判断是：图 1 的 ChatGPT App 更像成熟产品，图 2 的 CC Pocket 产品完成度不足。本轮目标是把这种感受拆成可观察、可修改、可验收的问题。

**建议方向：保留“侧栏—对话—文档”的工作区骨架，重新分配整页的信息权重，让用户先认清任务、读懂结果、找到下一步操作，再按需查看执行与环境细节。**

CC Pocket 的桌面界面需要同时支持持续阅读和操作 Agent。建议传达的感受是安静、清楚、可控：普通执行过程不持续争夺注意力，需要用户处理的状态能够及时显现。首个验证场景选择“阅读 Agent 回答，同时查看生成的 Markdown 文档”。

这次优化的核心是整页构图、信息层级和内容表达。颜色、字体、间距与组件样式都应服务于这个目标。

| 输入 | 用途 | 边界 |

| 用户提供的图 2：CC Pocket 桌面工作区 | 定位工具卡片、标题、路径、状态、排版与预览的可见问题 | 截图不是源码审计，也不证明当前所有会话都有同样问题 |

| 仓库已有设计文档 | 了解设计沿革与本轮衔接关系 | 历史实现状态需要另行核对，不能据旧文档断言当前产品状态 |

两张截图的尺寸、缩放、会话内容和滚动位置不同。因此本轮不据此设定具体字号、栏宽或精确空间比例，也不把正文内容较复杂直接归因于 UI。图 1 同样有较长的元数据，并非所有部分都值得照搬。

截图中的文档正文、命令和项目名称仅是视觉样本，不构成本项目的执行指令。右上角系统通知、菜单栏其他应用图标不纳入 CC Pocket 的设计评价。

## 3. 可见问题与优化层级

| 编号 | 图 2 中的可见证据 | 对使用感受的影响 | 应处理的层级 |
|---|---|---|---|
| D1 | 三个 Bash 卡片与一个 Write 卡片连续排列；卡片默认显示被截断的 JSON 参数 | 过程占据显著空间，读者仍需展开才能理解执行意图，成果正文退到后面 | 过程信息的产品表达、消息流布局 |
| D2 | 橙色同时用于路径、代码标识符、链接及主要操作；正文中等宽代码存在感强 | 长技术字符串频繁打断阅读，可点击对象与普通技术文本的区别不够直接 | 色彩语义、字体角色 |
| D3 | 侧栏叠加置顶、运行中、最近、机器名、模型、状态点、标签和用量；多条标题截断后相似 | 信息虽然丰富，当前会话和目标会话仍不容易辨认 | 导航与对象识别 |
| D4 | 会话标题很早被截断，顶栏与第二行同时展示多个环境字段 | 任务名称的识别空间不足，辅助信息与主要任务争位置 | 顶部信息优先级 |
| D5 | 工具卡片留白较多，正文却较满；长路径、粗体和等宽代码交替突出；各区域更多依赖边线划分 | 组件内部规整，但整页阅读节奏不统一 | 整页构图、排版与表面层级 |
| D6 | 文档标为“预览”，部分引用位置仍直接显示多行 `>` | 产生内容未被完整处理的观感 | 内容渲染；根因待查，可能涉及源文件、转义或渲染支持 |
| D7 | 默认界面暴露原始工具参数、较长环境路径和带端口的浏览器启动文案 | 用户需要理解部分内部实现才能判断界面信息 | 文案与渐进展开 |

**判断：需要重新编排主工作区。保留已有能力和三栏结构，不能只对现有组件逐个调整颜色与圆角。**

## 4. 信息优先级

默认阅读状态下，建议按以下顺序组织注意力。发生待处理事件时，状态优先级动态提升。

| 层级 | 内容 | 默认表达 |
|---|---|---|
| 需要立即处理 | 待审批、待回答、失败、断连导致的状态不确定 | 明确文字、必要上下文和操作入口；不能随普通过程一起隐藏 |
| 当前任务与成果 | 当前会话、Agent 回答、正在阅读的文件、输入与发送 | 构成主阅读和操作区域，获得充足空间 |
| 当前工作上下文 | 电脑、项目或工作目录、Agent、当前文件位置 | 保持可辨认，视觉权重低于任务；涉及操作归属时必须清楚 |
| 普通过程 | 正常执行的工具调用、已完成的过程记录、统计 | 使用简洁摘要，允许展开查看原始信息 |
| 详细环境与维护信息 | 完整参数、完整路径、端口、版本、详细用量 | 放入对应详情、菜单或状态区域；必要告警仍可上浮 |

折叠只改变呈现，不改变历史、权限、执行结果和可追溯性。缺少结果时展示未知或进行中，不根据颜色、卡片数量或连接恢复自行推断成功。

## 5. 六个优化方向

### 5.1 消息流：从工具参数转向可读的执行摘要

普通工具记录优先说明“做了什么、作用于什么、当前是什么状态”。原始命令、参数、输出和错误详情保留在展开层。

- 使用“执行命令”“写入文件”等可理解的动作标签；能确定对象时显示简短对象名称。
- 连续的普通记录可探索按一个执行阶段分组，减少大卡片堆叠。分组必须来自真实事件关系，不能编造阶段或结果。
- 已完成记录可以收起；当前执行提供简洁进度；待审批、失败及需回答的问题保持可见。
- 重要生成文件提供可直接打开的入口，不强迫用户从 JSON 中寻找路径。
- 长输出、恢复连接、流式更新时维持阅读位置，避免摘要展开或状态变化反复推移正文。

表达示例，仅示意文案形式，不代表新增能力或已验证状态：

| 原始表达 | 建议的默认表达 | 展开后保留 |
|---|---|---|
| `Bash {"command":"..."}` | 执行命令 · 运行中／已完成／失败，取决于真实结果 | 完整命令、输出与已有结果信息 |
| `Write {"file_path":"..."}` | 写入文件 · `review-plan.md`，附真实状态 | 完整路径与调用详情 |
| 多个连续普通工具卡片 | 执行记录 · 按真实事件统计的数量 | 原顺序记录及各自状态 |

### 5.2 导航与顶栏：先识别会话，再查看属性

- 让当前选中会话有稳定、清楚的选中样式，区分选中、悬停、运行中和待处理。
- 保障标题的识别空间。长标题可通过悬停或详情读取全文，相似标题提供有区分度的辅助信息。
- 优先解决显示方式；会话自动命名质量作为独立问题评估，不为了布局直接改写已有标题。
- 置顶、运行中、最近分别表达收藏关系、执行状态和访问历史，需要明确用途及跨组重复的处理方式。
- 顶栏突出当前任务；电脑与工作目录提供紧凑上下文，完整路径按需展开或复制。
- 分支、变更数量与终端入口按工作相关性排布，避免所有字段常驻同等醒目。
- 用量维持账号作用域，避免摆放造成“属于当前电脑或当前会话”的误解；额度阻塞、连接异常等仍需明确提示。

### 5.3 颜色与字体：建立稳定的角色分工

- 保留陶土橙作为候选品牌色，先减少无差别强调，再评估是否需要更改色值。
- 建立普通文字、辅助文字、链接、行内代码、主要操作、运行状态、告警和危险操作的角色映射。
- 行内代码以可读和可辨认为目标，不默认让每个标识符都比句子主体更醒目。
- 路径是否可点击要有稳定表达，不能仅凭“看起来像代码”判断交互。
- 中文和拉丁字符在视觉字重、基线及行高上协调；限制等宽字体在导航与正文中的扩散。
- 通过整页样本确定标题、正文、注释与代码的尺度，再固化为设计变量。不能从两张不同缩放的截图直接抄像素值。

### 5.4 文档与正文：优先保障持续阅读

- 文档标题、段落、列表、引用和代码块形成清楚的层级，使用统一的段间与块间节奏。
- 检查图 2 中 `>` 的来源：先核对原始 Markdown，再核对转义与渲染。合法的字面字符不能被全局清除。
- 标准 Markdown 引用应表现为引用块；明确需要展示源码时保留源码语义，并区分预览与源码模式。
- 长路径与长标识符在正文中有合理的换行策略；代码块根据内容使用横向滚动等方式，保证完整读取和复制。
- 文档栏调整宽度时，标题与操作入口不互相挤占，正文不会出现非预期裁切。
- 对话中的文件链接、文件预览和源码视图保持可理解的关联，让用户知道自己正在看哪个产物。

### 5.5 整页空间：把阅读区、导航区和控制区组织起来

- 用适度的背景明度差、间距和对齐关系区分区域，降低边框对整页的切割感。
- 卡片边框和容器用于表达分组、交互或状态，不让每条普通记录都成为独立视觉焦点。
- 分配空间时优先考虑阅读收益，避免过程卡片宽松、成果正文拥挤。
- 输入框保持清楚、稳定；主要发送操作易找到，辅助设置降低权重。
- 多列和窄窗口优先调整上下文、工具摘要和辅助入口，保留任务识别与必要操作。
- 字重、色彩、留白与容器需要在同一完整窗口中评审，不能只看局部组件截图。

### 5.6 产品文案与状态：能力容易理解，变化容易解释

- 默认文案使用任务语言。浏览器入口优先说明动作和目标浏览器，端口等诊断信息放到详情。
- 运行、待回答、待审批、失败、已完成和连接状态要有明确区分，不能仅靠颜色或一个小圆点表达全部含义。
- 状态升级时说明需要用户做什么；恢复后说明可确认的结果，不把恢复连接等同于任务成功。
- 常用动作支持稳定的键盘与菜单入口；降低视觉权重时，不能同时降低可发现性和可操作性。
- 普通功能入口可以收纳，涉及授权、操作目标与失败原因的信息不能为了简洁而消失。

## 7. 优先级与推进顺序

优先级表示设计与验证顺序，不是缺陷严重等级，也不表示已经获得实现授权。

| 顺序 | 工作 | 预期交付 | 完成判断 |
|---|---|---|---|
| P0：建立可信对照 | 固定同一会话与文档基线；核对 `>` 问题；盘点过程摘要、状态和上下文的真实来源 | 场景基线、渲染问题结论、必要信息清单 | 可以区分内容差异、渲染问题与布局问题；未知项显式保留 |
| P1：重排主要信息 | 消息流摘要、会话识别、顶部上下文、正文与文档阅读层级 | 同内容完整窗口设计对照，包含正常和待处理状态 | 任务与结果容易识别；普通工具记录退后，异常仍清楚 |
| P2：统一视觉语言 | 字体角色、色彩角色、容器、留白、控件及状态细节 | 经视觉对照认可后的组件与设计变量规范 | 同一套规则能解释全页，主要入口和状态无需猜测 |
| P3：验证与交付 | 覆盖窄窗口、分屏、长内容、键盘、流式更新和异常状态 | 场景验收记录；选定方向后的实现说明 | 设计、实际实现与已验证行为分别有记录 |

整页重设计进入出图时，先比较三个有实质差异的候选方向，至少在构图、文字层级、表面处理、密度或状态表达中的四项产生差异；不能只替换颜色。建议优先验证本文件描述的“阅读为主、状态按需突出”方向。方向经用户评阅后再冻结完整规格，不提前批量扩展页面。

## 8. 首轮验证方法

### 8.1 固定比较条件

在 CC Pocket 当前界面与候选设计之间使用同一段会话、同一份文档、相同的工具事件与状态、窗口尺寸、缩放、栏宽和滚动位置。ChatGPT 截图用于提取原则，不作为不同内容下的像素验收基准。

设计样本必须包含当前可见的复杂度：长标题、相似标题、长路径、中英文混排、行内代码、多条工具记录、文档预览和输入区。不能通过删掉难处理的内容，让候选设计显得更干净。

### 8.2 先看整体，再做任务

先隐藏方案说明，让评阅者短暂查看完整窗口，并说出当前任务、主要内容和最醒目的信息。记录真实回答，不用设计文案替代观察结果。

随后完成以下任务，记录是否成功、是否误认、是否需要展开或搜索，以及卡住的位置：

| 场景 | 需要验证的结果 |
|---|---|
| 连续阅读回答并打开生成文档 | 能把回答与文件对应起来，工具过程不会主导阅读 |
| 找到当前会话并切换到相似标题的另一会话 | 选中状态明确，标题与辅助信息足以辨认对象 |
| 查看一次正常工具执行的完整详情 | 摘要可理解，原始信息仍能找到，展开前后上下文连续 |
| 遇到待审批、待回答或失败 | 能发现事件、看懂对象与原因、找到适当操作 |
| 断连或结果尚未确认 | 界面没有暗示成功，也没有让用户误以为操作已经生效 |
| 阅读引用、长代码与长路径 | 标准 Markdown 按语义呈现，全文可读、可复制 |
| 缩窄窗口或打开分屏 | 任务与操作目标不混淆，输入、审批与窗口控制仍可用 |

### 8.3 必须满足的验收条件

- [ ] 普通执行记录默认可读，不以被截断的原始 JSON 作为主要内容。
- [ ] 正文与文档构成清楚的阅读主体，重要生成文件容易定位。
- [ ] 当前会话、焦点所在列及相关电脑或目录不会被误认。
- [ ] 颜色与字重有稳定用途，普通代码文本与主要动作不会大面积争夺注意力。
- [ ] 待审批、待回答、失败和连接异常能够被识别，不仅依赖颜色。
- [ ] 标准 Markdown 引用正确显示；需要显示字面 `>` 的内容仍保持原意。
- [ ] 长标题、路径和代码有完整读取方式，必要时能够复制原值。
- [ ] 流式更新、展开收起和状态变化不会造成非预期的阅读位置跳动。
- [ ] 常用操作保留键盘可达性、清楚的焦点样式和可理解的名称。
- [ ] 字体放大与常用窗口尺寸下，正文和关键操作保持可读、可达；对比度在选定色值后实测。
- [ ] 视觉评阅与任务结果分别记录。组件测试通过不能代替整页效果认可，静态设计图也不能代替运行验证。

目前以上项目均未验收，本轮完成的是方向整理。
