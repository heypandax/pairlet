# 慢链路韧性：丢包线路上的会话打开与转写

状态：第一期（不改协议）方案已定，实施中；第二期（压缩、小首窗）待单独设计与安全评审。2026-10-06（本机时区）。实现状态以源码为准。

来源：维护者反馈「会话打开和转写响应都很慢」。只读诊断的原始证据、时间线与复现脚本在本机 `_local/perf-2026-10-06/`，不入库；本文只保留脱敏后的结论与决定。

## 1. 结论

慢在传输，不在 daemon，也不在转写引擎。daemon 读一窗历史只要十几到两百毫秒，转写推理约 0.6 秒。问题出在手机与 relay 之间的跨境线路，以及 App 里两个把「慢」放大成「永远打不开」的定时器。

| 事实 | 实测 |
|---|---|
| relay 与大陆运营商之间的丢包随包长上升 | 小包约 5–10%，满尺寸包 15–53% |
| relay 到手机方向，一窗历史（约 73 KB） | 2.3 秒以上 |
| 同方向 135 KB | 6–16 秒 |
| 批量传输的重传比例 | 约 25% |
| 一窗 100 行历史 / 一个项目的会话列表 | 约 73 KB / 约 35 KB，协议目前没有压缩 |
| 增量历史帧的最大值 | 1.48 MB（带图），当时等了 21.5 秒后用户退出 |

事故窗口内，同一个会话被打开 4 次，73 KB 的历史发了 4 次，一次都没有被手机确认；一段转写 1.4 秒就转完了，结果却随着被重建的连接作废。

## 2. 为什么慢会变成打不开

一条连接上的帧按顺序到达。大帧在丢包线路上要重传很久，排在它后面的小帧（会话确认、转写结果、审批列表）全部跟着等，期间手机收不到任何一帧完整的下行。

1. **静默看门狗（#298）把慢当成了死。** `RelayE2EConnection` 规定「已发出至少 3 帧且 20 秒没有任何下行」就整条连接重建。前台每 3 秒轮询一次审批列表，所以第一个条件恒成立，只要下行静默 20 秒就必然触发。重建时 relay 丢掉在途回包，手机重新请求整窗历史，新的一窗又在 20 秒内到不了，于是每 20 秒重建一轮。
2. **打开超时的静默重放（#340）让字节翻倍。** 8 秒没有收到 `SessionLive` 就把同一个 `OpenSession` 再发一次，daemon 于是把同一窗历史再排一遍队。可是在一条按序到达的连接上，第一份回包一定排在重放的回包前面，重放不可能更快，只会让队列更长。
3. **增量历史没有上限。** 首窗有行数上限，增量路径没有，带图的会话会产生上兆的单帧，在这条线路上基本送不到。

看门狗原本要治的是另一种情况：daemon 丢了这台设备的会话（relay 抖动、daemon 重启），手机发什么都石沉大海。这种僵尸链路必须保住自愈，所以不能简单地把 20 秒调大。

## 3. 第一期：不改协议的三项修复

三项互相独立，可以分开合入。App 两项随下一个 App 版本到达用户；daemon 一项随 daemon 更新到达，对已经装好的旧 App 同样生效。

### 3.1 App：静默看门狗按证据放宽

位置：`mobile/composeApp/src/commonMain/kotlin/dev/ccpocket/app/net/RelayE2EConnection.kt`，`silenceDeafTripped` 与写协程里的调用点。

依据是一条已经写在代码注释里的事实：握手完成本身就证明 daemon 持有这台设备的会话。僵尸链路要在握手之后再丢一次会话才会出现，这是少见的事；大帧卡在路上在丢包线路上却是常态。所以用两个时间量来放宽：

- **连接年龄。** 握手完成不到 60 秒的连接，daemon 刚刚才证明过自己在，静默更像是大帧在路上，窗口乘 2。握手已久的连接突然静默，最像僵尸链路，窗口保持 20 秒不变。
- **近期触发记忆。** 静默看门狗每触发一次，`strikes` 加 1；距离上一次触发满 5 分钟才清零。重建之后很快又静默，说明重建没有用，窗口逐次翻倍。

规则：

```
窗口 = min( 20 秒 × 2^strikes × (连接年龄 < 60 秒 ? 2 : 1), 160 秒 )
```

| strikes | 连接年龄 | 窗口 |
|---|---|---|
| 0 | 60 秒及以上 | 20 秒（与现状相同） |
| 0 | 不到 60 秒 | 40 秒 |
| 1 | 60 秒及以上 | 40 秒 |
| 1 | 不到 60 秒 | 80 秒 |
| 2 | 60 秒及以上 | 80 秒 |
| 2 及以上 | 不到 60 秒 | 160 秒（上限） |

- `strikes` 是连接对象上的计数，跨重连保留；只按「距上次触发是否满 5 分钟」清零，判断可以惰性做。
- 任意一帧传输帧成功解密，仍然像现在一样重置静默计时和已发送计数，但**不影响** `strikes`。
- 被新连接取代的旧连接触发时不发信号，也不计 strike。
- 解密失败那一半（#146，连续 3 帧解不开）不动，也不影响 `strikes`。
- 窗口计算写成纯函数，和现有的 `silenceDeafTripped` 一样可以直接单测。

2026-10-06 修订：初稿用「本连接是否收到过下行」区分新旧连接，并在收到任意下行时清零 `strikes`。实现时发现 daemon 每次握手后都会立刻补发一帧 `DaemonInfo`，新连接一个往返之内就算收到过下行，事故里「重建 → `DaemonInfo` 到达 → 大历史帧卡住」的循环因此攒不起任何放宽。改为上面的连接年龄与触发记忆。

### 3.2 App：链路静默时不重放打开请求，并如实归因

位置：`PocketRepository` 的打开看门狗（`SESSION_OPEN_TIMEOUT_MS` 之后的那段判断）。

- 两个传输各自暴露一个只增的「已解密下行帧数」。发出 `OpenSession` 前记下当前值。
- 8 秒到期、连接仍是 Ready 时，先看这个数有没有变：
  - **没变（链路静默）**：不重放。再等 `SESSION_OPEN_SILENT_LINK_TIMEOUT_MS`（12 秒，合计 20 秒），仍没有答复就以 `OpenFailure.LINK` 结束，`retried = false`。理由：回包如果在路上，重放帮不上忙；如果请求掉进了僵尸链路，重放同样会被丢，看门狗会在它自己的窗口里重建连接。
  - **变了（daemon 在答别的，偏偏没答这次打开）**：保持现状，对恢复类打开静默重放一次，再等 4 秒，失败归因 `COMPUTER`。
- 新会话（`resumeId == null`）仍然不重放，理由见 #340 的注释，不变。
- 界面、文案、埋点事件名都不变；`TelKey.Link` 在静默链路上会如实报 `down`。

### 3.3 daemon：历史帧软上限

位置：`daemon/src/main/kotlin/dev/ccpocket/daemon/server/FrameFitter.kt`。

现有的 `FrameFitter` 只在帧超过对端 WebSocket 硬上限时才动手，而且会先舍弃行内附加内容（图片、子代理报告）再丢行。软上限是另一回事：帧没有超限，只是在丢包线路上太大。所以它只做一件无损的事。

- 对 `ConvoHistory`（首窗与增量）和 `ConvoHistoryPage`：编码后超过 `HISTORY_SOFT_CAP_BYTES`（256 KB）时，**只从最旧的一端整行丢弃**，直到不超过上限或只剩 `HISTORY_SOFT_MIN_ROWS`（20）行。
- 丢过行的帧按现有规则重新锚定：`firstSeq` 取保留的第一行，`hasMore = true`，`delta = false`。被丢掉的行由手机向上翻页取回，不丢数据。
- 软上限**不舍弃**图片等行内附加内容；那仍然只是硬上限的最后手段。
- 保留的第一行没有 `seq`（后端不支持翻页）时不做软裁剪。
- 20 行仍然超过软上限就原样交给后面的硬上限逻辑。
- 裁剪时记一行日志：帧类型、裁剪前后的行数与字节数，不含内容。

保留至少 20 行，是因为手机端在窗口太短、填不满一屏时还不会自动向上翻页（见第 4 节 E）。普通会话一行约 0.7 KB，100 行约 73 KB，不会触到软上限；触到的是带大量图片或长输出的会话。

## 4. 明确不在第一期做的

| 项 | 为什么后置 | 重启条件 |
|---|---|---|
| D 先压缩再加密 | 改协议，要过加密评审（压缩与加密叠加的长度侧信道）和线协议兼容评审。实测一窗历史可从 73 KB 压到约 19.5 KB，是收益最大的一项 | 第一期合入后单独出设计：按 `ClientCaps` 协商、逐帧独立压缩（不跨帧共享上下文）、只压缩超过阈值的帧 |
| E 首屏小窗口加后台补齐 | daemon 的首窗预算机制已合入但默认关闭，因为手机端短窗口不会自动翻页 | 先补手机端「窗口填不满一屏就自动取上一页」，再启用预算 |
| F 小帧优先、大帧分片 | 要改 daemon 的单队列出站，分片要改协议 | 与 D 一起评估；压缩之后大帧少了，可能不再需要 |
| daemon 对同一连接上重复的打开不重发历史 | relay 设备的出站端按设备而不是按连接标识，判断错一次就是空白会话；3.2 已经从手机侧去掉了重放的主要来源 | 旧 App 仍在大量使用且数据表明重放仍是字节大头 |
| H relay 到大陆的线路 | 运维与成本决定，所有大陆用户共用这段线路 | 负责人决定 |
| I 音频上行去掉 base64 | 收益小 | 与 D 的协议改动一并考虑 |

在家时的根治办法不是这些修复，而是局域网直连（#403、#404、#405 与已写入本机的直连偏好）：手机直连电脑，不再出境。第一期解决的是不在同一个网络时，以及所有经 relay 的大陆用户。
