# 慢链路韧性：丢包线路上的会话打开与转写

状态：第一期已实现并合入本地 main（2026-10-06，未发版；真机验收待做）；第二期的「小首窗」与「图片两档」见第 6 节，已实现并合入本地 main（2026-10-06，未发版；真机验收待做）；压缩仍待单独设计与安全评审。2026-10-06（本机时区）。实现状态以源码为准。

来源：维护者反馈「会话打开和转写响应都很慢」。只读诊断的原始证据、时间线与复现脚本在本机 `_local/perf-2026-10-06/`，不入库；本文只保留脱敏后的结论与决定。

## 1. 结论

慢在传输，不在 daemon，也不在转写引擎。daemon 读一窗历史只要十几到两百毫秒，转写推理约 0.6 秒。问题出在手机与 relay 之间的跨境线路，以及 App 里两个把「慢」放大成「永远打不开」的定时器。

| 事实 | 实测 |
|---|---|
| relay 与大陆运营商之间的丢包随包长上升 | 小包约 5–10%，满尺寸包 15–53% |
| relay 到手机方向，一窗历史（约 73 KB） | 2.3 秒以上 |
| 同方向 135 KB | 6–16 秒 |
| 批量传输的重传比例 | 约 25% |
| 一窗 100 行历史 / 一个项目的会话列表 | 约 73 KB / 约 35 KB，协议目前没有压缩 |
| 增量历史帧的最大值 | 1.48 MB（带图），当时等了 21.5 秒后用户退出 |

事故窗口内，同一个会话被打开 4 次，73 KB 的历史发了 4 次，一次都没有被手机确认；一段转写 1.4 秒就转完了，结果却随着被重建的连接作废。

## 2. 为什么慢会变成打不开

一条连接上的帧按顺序到达。大帧在丢包线路上要重传很久，排在它后面的小帧（会话确认、转写结果、审批列表）全部跟着等，期间手机收不到任何一帧完整的下行。

1. **静默看门狗（#298）把慢当成了死。** `RelayE2EConnection` 规定「已发出至少 3 帧且 20 秒没有任何下行」就整条连接重建。前台每 3 秒轮询一次审批列表，所以第一个条件恒成立，只要下行静默 20 秒就必然触发。重建时 relay 丢掉在途回包，手机重新请求整窗历史，新的一窗又在 20 秒内到不了，于是每 20 秒重建一轮。
2. **打开超时的静默重放（#340）让字节翻倍。** 8 秒没有收到 `SessionLive` 就把同一个 `OpenSession` 再发一次，daemon 于是把同一窗历史再排一遍队。可是在一条按序到达的连接上，第一份回包一定排在重放的回包前面，重放不可能更快，只会让队列更长。
3. **增量历史没有上限。** 首窗有行数上限，增量路径没有，带图的会话会产生上兆的单帧，在这条线路上基本送不到。

看门狗原本要治的是另一种情况：daemon 丢了这台设备的会话（relay 抖动、daemon 重启），手机发什么都石沉大海。这种僵尸链路必须保住自愈，所以不能简单地把 20 秒调大。

## 3. 第一期：不改协议的三项修复

三项互相独立，可以分开合入。App 两项随下一个 App 版本到达用户；daemon 一项随 daemon 更新到达，对已经装好的旧 App 同样生效。

### 3.1 App：静默看门狗按证据放宽

位置：`mobile/composeApp/src/commonMain/kotlin/dev/ccpocket/app/net/RelayE2EConnection.kt`，`silenceDeafTripped` 与写协程里的调用点。

依据是一条已经写在代码注释里的事实：握手完成本身就证明 daemon 持有这台设备的会话。僵尸链路要在握手之后再丢一次会话才会出现，这是少见的事；大帧卡在路上在丢包线路上却是常态。所以用两个时间量来放宽：

- **连接年龄。** 握手完成不到 60 秒的连接，daemon 刚刚才证明过自己在，静默更像是大帧在路上，窗口乘 2。握手已久的连接突然静默，最像僵尸链路，窗口保持 20 秒不变。
- **近期触发记忆。** 静默看门狗每触发一次，`strikes` 加 1；距离上一次触发满 5 分钟才清零。重建之后很快又静默，说明重建没有用，窗口逐次翻倍。

规则：

```
窗口 = min( 20 秒 × 2^strikes × (连接年龄 < 60 秒 ? 2 : 1), 160 秒 )
```

| strikes | 连接年龄 | 窗口 |
|---|---|---|
| 0 | 60 秒及以上 | 20 秒（与现状相同） |
| 0 | 不到 60 秒 | 40 秒 |
| 1 | 60 秒及以上 | 40 秒 |
| 1 | 不到 60 秒 | 80 秒 |
| 2 | 60 秒及以上 | 80 秒 |
| 2 及以上 | 不到 60 秒 | 160 秒（上限） |

- `strikes` 是连接对象上的计数，跨重连保留；只按「距上次触发是否满 5 分钟」清零，判断可以惰性做。
- 连接年龄取**这一次静默开始时**（握手完成，或最近一次解密成功的时刻）的年龄，不取检查那一刻的：要判断的是这段静默，在年轻连接上开始的静默整段都更像回包在路上。按检查时刻算，翻倍会在连接满一分钟时突然失效。
- `strikes` 属于它被记下时连接的那台电脑。连接对象在切换电脑后继续使用，连到另一台电脑的连接从 0 开始，不继承上一台的记忆。
- 任意一帧传输帧成功解密，仍然像现在一样重置静默计时和已发送计数，但**不影响** `strikes`。
- 被新连接取代的旧连接触发时不发信号，也不计 strike。
- 解密失败那一半（#146，连续 3 帧解不开）不动，也不影响 `strikes`。
- 窗口计算写成纯函数，和现有的 `silenceDeafTripped` 一样可以直接单测。

2026-10-06 修订：初稿用「本连接是否收到过下行」区分新旧连接，并在收到任意下行时清零 `strikes`。实现时发现 daemon 每次握手后都会立刻补发一帧 `DaemonInfo`，新连接一个往返之内就算收到过下行，事故里「重建 → `DaemonInfo` 到达 → 大历史帧卡住」的循环因此攒不起任何放宽。改为上面的连接年龄与触发记忆。

### 3.2 App：链路静默时不重放打开请求，并如实归因

位置：`PocketRepository` 的打开看门狗（`SESSION_OPEN_TIMEOUT_MS` 之后的那段判断）。

- 两个传输各自暴露一个只增的「已解密下行帧数」。发出 `OpenSession` 前记下当前值。
- 8 秒到期、连接仍是 Ready 时，先看这个数有没有变：
  - **没变（链路静默）**：不重放。再等 `SESSION_OPEN_SILENT_LINK_TIMEOUT_MS`（12 秒，合计 20 秒），仍没有答复就以 `OpenFailure.LINK` 结束，`retried = false`。理由：回包如果在路上，重放帮不上忙；如果请求掉进了僵尸链路，重放同样会被丢，看门狗会在它自己的窗口里重建连接。
  - **变了（daemon 在答别的，偏偏没答这次打开）**：保持现状，对恢复类打开静默重放一次，再等 4 秒，失败归因 `COMPUTER`。
- 新会话（`resumeId == null`）仍然不重放，理由见 #340 的注释，不变。
- 界面、文案、埋点事件名都不变；`TelKey.Link` 在静默链路上会如实报 `down`。

### 3.3 daemon：历史帧软上限

位置：`daemon/src/main/kotlin/dev/ccpocket/daemon/server/FrameFitter.kt`。

现有的 `FrameFitter` 只在帧超过对端 WebSocket 硬上限时才动手，而且会先舍弃行内附加内容（图片、子代理报告）再丢行。软上限是另一回事：帧没有超限，只是在丢包线路上太大。所以它只做一件无损的事。

- 对 `ConvoHistory`（首窗与增量）和 `ConvoHistoryPage`：编码后超过 `HISTORY_SOFT_CAP_BYTES`（256 KB）时，**只从最旧的一端整行丢弃**，直到不超过上限或只剩 `HISTORY_SOFT_MIN_ROWS`（20）行。
- 丢过行的帧按现有规则重新锚定：`firstSeq` 取保留的第一行，`hasMore = true`，`delta = false`。被丢掉的行由手机向上翻页取回，不丢数据。
- 软上限**不舍弃**图片等行内附加内容；那仍然只是硬上限的最后手段。
- 保留的第一行没有 `seq`（后端不支持翻页）时不做软裁剪。
- 20 行仍然超过软上限就原样交给后面的硬上限逻辑。
- 裁剪时记一行日志：帧类型、裁剪前后的行数与字节数，不含内容。

保留至少 20 行，是因为手机端在窗口太短、填不满一屏时还不会自动向上翻页（见第 4 节 E）。普通会话一行约 0.7 KB，100 行约 73 KB，不会触到软上限；触到的是带大量图片或长输出的会话。

## 6. 第二期：小首窗与图片两档（改协议）

来源：第一期之后，维护者在外面仍然打不开一个会话。实测那个会话的首窗是 394 KB，其中两张截图占 307 KB；软上限裁完仍有约 210 KB。行数上限管不住字节，1024 像素的缩略图是按全屏查看定的尺寸，而聊天里的图片格子只有 92 dp 高。

| 同一个会话 | 首窗 |
|---|---|
| 第一期之前，最新 100 行 | 394 KB |
| 只取最新 30 行 | 26 KB |
| 两张图改成预览 | 306 KB → 约 29 KB |

两件事都是无损的：更早的行和原图都只差一次请求。两件事也都按**连接**声明、在**发往每个连接的最后一道**（`FrameFitter`）执行，因为一窗历史会扇出给会话上的所有客户端，只有在那里才知道对端要不要。没有声明的连接收到的帧与以前逐字节相同。

### 6.1 协议

全部是向后兼容的新增。

- `ClientCaps.supportsImagePreviews`：这个连接把带 `ref` 的图片当预览显示，并在用户打开时自己取原图。
- `ClientCaps.supportsShortHistoryWindow`：这个连接在窗口填不满一屏时会自己向上翻页。只在滚到顶才翻页的客户端不能声明，否则会停在短窗口上。
- `DaemonInfo.supportsLeanHistory`：这个 daemon 认上面两个能力。旧 daemon 没有这个字段，App 据此知道它的历史分页还是整页一百行，不会自己连取几页。
- `ImageData.ref`：只出现在 daemon 发往已声明连接的图片上，表示 `base64` 是预览。值是原图字节的 SHA-256 的前 22 个 base64url 字符（`ImageRefs.of`）。上行图片和旧 daemon 的图片没有这个字段，编码与以前相同。
- `FetchImage(convoId, ref, seq?, index, requestId?)` 与唯一应答 `ImageContent(convoId, ref, image?, error?, requestId?)`。`seq` 是那一行的转录游标，`index` 是图片在行内的位置。错误码固定为 `no_conversation`、`unavailable`、`bad_ref`。

`ref` 取内容哈希有一个实际用途：手机刚发出去的图片只有本地字节，回放回来的是预览，两者字节不同；`TranscriptMerge` 用 `ImageRefs.of(本地字节) == 预览的 ref` 认出是同一张，纯图片的待确认气泡不会多出一个分身。

### 6.2 daemon

位置：`daemon/.../media/ImagePreviews.kt`、`server/FrameFitter.kt`、`session/SessionRegistry.fetchImage`。

预览（`FrameFitter.Lean.imagePreviews`）：

- 历史行、历史分页、实时工具结果上的图片一律换成预览。工具结果长边 384，提示词附件长边 480（气泡里显示得更大）。JPEG，按一半一半逐级缩小后再定尺寸，带透明的铺在 App 的深色底上。
- base64 不超过 16 KB 的图原样发，不带 `ref`。解不开、不是图片、预览省不到三成的，也原样发。预览绝不能让图片丢掉。
- 原图留在内存里（按字节上限的 LRU，约 48 MB），键是「会话 + ref」。不落盘：转录本身就是持久副本。
- `FetchImage` 只对当前开着的会话或只读观察视图作答。内存里有就直接回；没有而请求带了 `seq`，就按游标把那一行从转录里读回来，先按内容哈希找，找不到且只有一行带图时退回按位置取。受限凭据（IM 桥接、执行链接）的入口白名单默认拒绝这个新帧。

小首窗（`FrameFitter.Lean.shortHistoryWindow`），在预览之后量字节：

| 帧 | 超过多少才动 | 收到多少 | 最少保留 |
|---|---|---|---|
| 首窗（非增量 `ConvoHistory`） | 32 KB | 32 KB | 8 行 |
| 增量 `ConvoHistory` | 64 KB | 32 KB，并改为非增量 | 8 行 |
| 更早的一页 `ConvoHistoryPage` | 64 KB | 64 KB | 8 行 |

- 只从最旧的一端整行丢弃，`firstSeq` 落在保留的第一行，`hasMore = true`。与第一期软上限是同一个函数（`trimOldestRows`），软上限对所有连接照常生效。
- 切口不落在同一个源行内部。一行转录可以产出多行（一段回复加几个工具调用），它们共用游标，而分页只回 `firstSeq` 之前的行，切在中间会丢掉前半。这一条同时修了软上限里同样的问题。
- 保留的第一行必须有游标。没有游标的行（压缩摘要）留给更早的一页；所有行都没有游标的后端（不支持分页）整窗不动。
- `ImageContent` 超过对端声明的帧上限时改回 `unavailable`，不原样发出（提示词附件的原图最大约 600 KB）。
- 预览做不成或不划算的图也记入缓存，不在每次发帧时重试。
- 顺带：`ImageThumbnail` 只在图片真的有透明像素时才保留 PNG。调色板透明（PNG-8、GIF）按解析后的像素判断，仍保留 PNG。截图工具常写出带 alpha 通道但全不透明的 PNG，实测同尺寸比 JPEG 大一倍。

### 6.3 App

- 手机和平板声明两个能力（`supportsLeanHistory()`）。桌面端暂不声明：它的分屏列还不会翻页，声明了会停在短窗口上。桌面端因此保持整窗与 1024 像素的图。
- 自动补页：`ui/chat/HistoryAutoPage.kt` 的 `wantsOlderHistory`。条件是「停在顶部（滚上来的，或根本滚不动）、首次落位已完成、上面还有、刚给的行已经完成测量」。每落一页重新判断一次，直到填满一屏或没有更早的历史。原来的收集器只看位置，滚不动的列表位置不变，所以短窗口从不翻页。
- 自动补页有预算（`ShortWindowPaging`）。工具行会折叠，一页四十个工具调用可能整页折进屏幕上已有的那一行，窗口和之前一样短；只按「填满为止」会把整个会话翻完。所以滚不动的窗口最多自己取 3 页（对没有通告 `supportsLeanHistory` 的旧 daemon 仍是以前的 1 页），而且上一页没有让屏幕多出任何一行就停。读者展开折叠（行数变多）会重新放行；读者自己滚到顶的翻页不受预算限制。
- 预算按窗口计：同一个会话收到新的整窗（重连后的重放、长时间离开后的增量被改成首窗）时重新开始，`historyWindowGen` 是这个信号。
- 读者自己滚到顶的翻页保持原样：到顶取一页，再要下一页需要再滚一次。流式输出或一页落地都不会被当成又一次到顶。
- 一页应答必须对得上正在等的那次请求（`answersOutstandingPage`）：应答里的行都在请求的游标之前。慢链路上同一页可能被要两次，第二份应答到达时游标已经下移，以前会被当成下一页再插一遍，并把真正的下一页当成没人要的丢掉。
- 页丢了的重试：仍停在原处且 30 秒没有任何变化时再要一次。慢而未丢的页随时到随时收，不重复要：仓库层对同一页的请求有 25 秒冷却，流式输出让列表反复重新判断时也不会把同一页再发一遍。
- 原图：查看器翻到某一页时，若那张是预览就发 `FetchImage`，到了原地换上；期间显示「正在加载原图…」，取不到显示「暂时取不到原图，当前显示的是预览」。同一张图同时只有一个请求，45 秒无应答放弃。取回的原图最多留 8 张，离开会话时与转录一起清掉。

### 6.4 明确没做的

| 项 | 说明 |
|---|---|
| 桌面端的预览与小首窗 | 需要先给分屏列补翻页，再让桌面查看器支持换原图 |
| 缩略图落盘缓存 | 只省 daemon 的计算，不省传输；原图丢了可以从转录读回 |
| 自动把可见预览升级为原图 | 会把省下的字节又发回去；只在用户打开时取 |
| 先压缩再加密（D） | 仍需加密评审。小首窗之后首屏约 26 KB，压缩后约 8 KB |
