# 核心列表与会话体验 · 功能优化方案 v1

日期：2026-09-22（本机时区）。状态：产品提案，未实施。依据：用户提供的核心界面录屏、当前工作区源码及相关设计说明。设计与验证状态见 [README](README.md)，设计约束见 [brief](DESIGN_BRIEF.md)。

## 目标与范围

让用户在手机上快速回答三件事：该继续哪件任务、打开后在等什么、当前结果是否需要自己处理。保持已有项目导航、Agent 操作与零知识 E2E 架构，沿用深浅主题和现有设计系统。

本轮交付界面设计和功能方案，不修改产品代码，不创建 Issue，不发版或部署。视觉优化可以独立落地；历史读取性能、缓存和数据字段调整需按证据另行评估。

## 现状：观察与事实分开

| 内容 | 已确认 | 不应据此推断 |
|---|---|---|
| 打开已有会话 | 单次录屏约第 4 秒进入，第 11 秒多出现正文；约 7 秒空白 | 不能推出普遍耗时、网络故障、relay 故障或解析阻塞 |
| 首屏定位 | `App.kt` 有 `landed` 控制，180ms 后放开；收到并布局消息后定位末尾 | 180ms 门控本身不能解释 7 秒延迟，需时序证据 |
| 打开过程 | `SessionLive` 后会撤销 `opening`；另有 `HistoryComplete` 和实际布局观测 | 已连接／已绑定会话不等于历史已呈现 |
| 执行过程 | 连续至少两项成功普通工具／已结束思考可折叠；失败、运行、未知工具及正文等会中断分组 | 并非缺少折叠功能；不能把散落工具跨正文重新拼组 |
| 会话状态 | 共享状态模型；审批、提问及真实失败优先；单纯运行不再新增聊天顶部状态条 | 不能从某条失败命令推断整个会话失败，也不能凭时间戳标“新结果” |
| 额度 | 当前 `QuotaStripSegment` 使用 `limit.percent` 显示已用；Claude 双窗口、Codex 账号级周窗口 | 文件顶部仍有历史“剩余”描述，不能将旧注释作为当前数字口径 |

设计中出现的机器、项目、消息和数字均为示例。本文无性能改善的实测结论。

## 优先级与实施拆分

| 优先级 | 工作包 | 用户收益 | 主要依赖 |
|---|---|---|---|
| P0 | 打开会话的可见加载与终态 | 不再把空白误认为卡死或空会话 | 打开身份、已有历史／布局信号及旧 daemon 降级 |
| P1 | 执行过程的默认阅读层级 | 更容易找到 Agent 的进展与结论 | 复用展示投影、保留原始消息和阅读锚点 |
| P1 | 列表继续入口和新建动作语义 | 更快继续任务，降低误建会话 | 现有会话目录、项目入口与统一状态模型 |
| P1 | 头部、输入区及额度语义 | 节省阅读空间、降低识别成本 | 现有上下文展开与额度明细 |
| P2 | 首屏耗时优化／有限本地缓存 | 缩短真实等待 | 分阶段耗时证据、身份隔离与缓存生命周期评估 |

建议先实施 P0 和不改变业务语义的 P1。P2 的方案必须由瓶颈数据决定，不能先假设需要新缓存或新协议。

## P0：会话打开与历史加载

### 产品状态

以下是拟议的展示状态，不直接替代现有执行状态或诊断对象：

| 状态 | 显示 | 进入／退出依据 | 可用操作 |
|---|---|---|---|
| 正在打开 | 标题立即呈现，正文区“正在打开会话…” | 用户打开意图；有效绑定后进入历史阶段 | 返回；保留草稿，不提前宣称可发送 |
| 正在加载历史 | “正在加载历史消息…”；静态骨架仅作占位，不用假消息 | 本次身份绑定且等待首屏内容／确认空历史 | 返回；已获得的真实内容可先显示 |
| 等待较久 | “历史消息仍在加载，可以返回后再查看” | 建议持续等待 3 秒后弱提示，阈值待实测调整 | 返回；不自动重启或重发业务请求 |
| 可阅读 | 正文出现；若仍有后续页，只在相应位置提示 | 当前视图的真实消息已布局 | 阅读、按现有能力输入与发送 |
| 确认空会话 | “还没有消息”及正常输入提示 | 已确认新会话无需历史，或匹配的历史完成结果确认为空 | 按既有输入能力操作 |
| 加载失败 | “历史消息加载失败”；有可靠分类时才补说明 | 匹配的明确历史失败；不得仅凭等待时间或空列表判断 | 返回；仅在安全历史重试能力成立时显示“重试加载” |
| 状态未确认 | “暂未确认历史加载结果” | 旧端缺确认能力、数据不足或诊断超时但无业务失败证据 | 保留已显示内容；查看连接信息／返回 |

3 秒是 UX 提案，不改变现有打开超时与诊断期限。超时提示不是“网络异常”，不能假装已经定位原因。明确断线可以使用真实连接提示，但历史加载与连接状态不能相互替代。

### 行为边界

- 打开 A 后切到 B，A 的迟到消息、失败和完成回执不能污染 B；关联机器、会话及本地视图代际。
- `SessionOpenObservation` 继续负责观测，展示层从业务事实派生；不得为了隐藏占位而伪造完成事件。
- 当前内容已有可读消息时不要重新清空为骨架，局部状态与真实内容可以并存。
- 旧 daemon 缺少确认帧时不能永久等新协议。已有内容照常显示；空且没有结束证据时显示状态未确认，不标成明确失败或已确认空历史。
- 保留既有新会话、恢复、外部观察和只读共享入口的发送限制。输入被拒绝时保留草稿；不因为“显示了输入框”推断已绑定可发送。
- “重试加载”是待实现能力：只重试读取，不重复执行用户 prompt、不创建会话、不 fork、不重启 Agent。未确认现有接口满足这些条件前，设计中的此按钮不得直接绑定 `OpenSession`。
- 回到前台按现有恢复机制重新评估状态，旧计时不得直接把新连接判成失败。

### 验收

1. 点击已有会话后下一次界面呈现就有加载反馈；3 秒后进入较慢提示，不出现无说明的空白。
2. 冷打开、热恢复、已确认空会话、旧 daemon、迟到成功、明确失败均表现不同且不误报。
3. 连续切换两台机器及两个会话，不串内容、不串终态。
4. 已显示内容、草稿、工具展开状态不因弱提示刷新而被清空。
5. 若提供重试，检查同一用户消息只执行一次、会话 ID 不变，并验证成功／失败／取消和重复点击。

## P1：执行过程的阅读层级

保持 `ChatPresentation` 的“展示投影”原则：原始消息、审批、复制全文、回退、消息顺序都不变。

- 现有成功工具与结束思考的连续分组继续默认折叠，建议文案为“执行过程 · 3 个工具 · 1 段思考”，图标与整行构成可点击展开入口。
- 失败、运行、结果未知工具继续在外展示，且终止当前折叠组；首版不把失败塞入“已完成”过程组。可用独立、紧凑的状态行降低体积。
- 默认工具行显示工具名、真实状态和可用的已有说明。没有说明时用工具名；不解析任意命令后编造“测试通过”“已安装”等业务结论。
- 原始参数和输出放在可展开详情中，长命令换行，支持复制；正文中的代码块仍是正文，不因为含代码就被折叠。
- 不跨 Agent／用户正文、审批、问题、计划、工作流、子任务、通知或回合边界重新排序聚合。保留这些对象各自的组件。
- 来源标签保留明确角色，可优化密度，但不合并独立用户回合，避免改变长按回退的作用范围。复制入口保持可发现，不做仅 hover 才可见的手机操作。
- 展开／收起保持当前阅读锚点；用户离开尾部后，新增输出不强行滚到底部。“回到最新”是显式动作，点击后恢复跟随。

验收：成功／失败／未知工具混合时，失败不被隐藏；连续正文、附件与工具顺序不变；展开 100 行输出不丢阅读位置；复制全文与回退消费原始数据；新增流式文字不抢走正在阅读的视口。

## P1：列表入口与状态

- 项目页首区建议使用“继续会话”，避免将可恢复的空闲会话统称“进行中”。任务标题允许两行，项目／分支放在次行或独立元信息行。
- 状态独立于标题排布：待审批、待回答、运行中、有新结果、空闲，优先沿用现有状态映射及真实来源。列表没有权威失败字段时，不从工具文本推导失败。
- “有新结果”沿用客户端观察到的运行→结束且用户在其他位置的转换；未观察到的会话不猜测未读结果。
- 不默认在本轮改变 daemon 提供的列表顺序，不增加新的跨设备全局优先级排序；排序需求可单独评估。
- 项目行主体进入项目会话列表；其独立动作明确叫“新建会话”，无障碍名包含项目名。全局入口建议“新建任务”，先选项目／配置，不与项目内动作混淆。
- 继续已有会话的卡片主体只打开，不隐式创建、fork 或发送消息。长标题截断时进入会话可读取完整标题。
- 若加入“最近进展”，只用现有明确可用的预览字段；未核实数据来源前首版保留项目、Agent、状态，不额外调模型生成摘要。

验收：已有会话和项目新建动作各自只触发一次正确回调；两行长标题与状态互不遮挡；列表与聊天的待处理状态一致；320pt 和放大字号下每项仍有独立触控区。

## P1：头部、输入区与额度

### 头部与输入

标题保持主要层级；常驻上下文精简为 Agent／项目等最少可识别信息，机器、模式、模型与完整路径放入展开区。危险或需决策的权限状态不能仅藏入详情。

审批／提问／真实失败沿用已有唯一顶部提示与既有决策入口；运行状态在输入区表达，不新增重复顶部横条。运行且输入为空时仅显示停止；运行有草稿时提供停止与排队发送，语义明确。上传、语音、附件和队列继续沿用现有行为。

上下文展开与键盘出现时，输入框与关键操作仍可达。长路径可换行和复制，不通过缩小字号解决布局问题；图标视觉尺寸可小于其至少 48dp 的实际触控区域。实现时同排图文遵守 `tightCenter`。

### 额度

- 紧凑条明确“已用”，Claude 5h＋7d、Codex 账号级 7d，与现有数据范围一致。空间不足时允许两行紧凑排列或按后端分行，不缩小数字到难读。
- 整条保持一个明细入口，明细解释窗口、已用数值及存在时的重置时间。不得用客户端时钟猜测缺失的服务端重置值。
- 无可用额度数据时沿用条消失的行为；某后端缺数据时只隐藏该后端，不显示 0%。旧值是否仍有效依现有数据状态判断，不伪装成刚刷新。
- 文案修正同时核查 `QuotaStrip.kt` 历史注释与当前实现的分歧；这属于后续代码清理项，本轮未改代码。

验收：2% 被理解为已用而非仅剩；两后端和单后端布局都可读；未知数据不变成 0；深浅主题、320pt 和大字号下明细仍可打开。

## P2：性能调查与候选优化

先复用现有观测，区分请求发起、会话绑定、历史读取／传输、客户端合并、首屏真实布局。按冷／热恢复、Agent、历史规模、端版本分组观察耗时，不能仅看接口已返回。报告阶段分桶耗时，不将真实 prompt、命令、账号路径或日志正文写入遥测。

按证据选择优化：读取耗时占主导时评估尾部读取；首屏 payload 过大时评估分页及最近消息优先；合并／布局占主导时检查批处理、投影和首屏定位。保留历史顺序、游标及“回到最新”语义。

本地缓存只在上述证据支持时评估：需绑定账号／机器／Agent／会话，设置容量与生命周期，退出配对或切换身份后不可串读；缓存画面必须说明更新状态，不能冒充实时结果。先核查现有内存工作集是否可复用，避免增加第二套真相来源。

性能目标在建立基线后再定；本轮不承诺“秒开”。若最终需要协议字段调整，进入独立实施方案，验证新旧端互通并做 wire 兼容审查。
