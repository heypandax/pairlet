# 推送注册确认与存量用户自动恢复方案

状态：已审核并实施（2026-09-19），protocol / relay / 公共客户端 / Android / Desktop 在 Windows 上通过 JVM 测试；iOS 原生部分已按固定接口实现但尚未在 macOS 上编译与真机验收。日期：2026-09-19。

实施时相对本文的三处调整：

1. relay 能力宣告沿用既有 `relayProtoV` 门控（新增 `PROTO_V_PUSH_ACK = 5`），不新增 `supportsPushRegistrationAck` 字段。
2. 「旧连接不覆盖新连接」由客户端保证：被取代的在途请求若已写出，新确认后补一次重确认。relay 对同一设备合法并存多条 socket（主连接 + LAN 补偿短拨号），服务端的「当前连接校验」会误杀短拨号路径，故 relay 只做认证身份、事务落库、按 socket 顺序处理。
3. 诊断不新增枚举，用现有 Stage / ErrorCode 组合区分各层；`PAIRING_ADDED` 仅对无持久记录的新配对触发预算重置，冷启动恢复的配对沿用持久冷却。

本文可交给 Claude Code 实施。审核通过前仅作为设计，不代表修改、部署、安装或现场测试授权。

## 1. 要解决的问题与边界

用户已安装 App、完成配对并正常使用，但 relay 没有该设备的推送 token，导致通知在进入 APNs 投递前被丢弃。修复必须同时覆盖新安装用户和已经陷入异常状态的老用户，不要求重装、重新配对或发送提示词才能恢复。

预期结果：用户已允许通知且具备可用连接时，App 自动获取系统当前 token，为每个允许接收通知的配对完成服务端登记并取得确认；暂时失败后有限重试，条件恢复后继续；用户主动关闭通知时尊重其选择。

本次范围：

- iOS 原生通知授权、APNs 注册、生命周期恢复与设置入口。
- 公共客户端的按配对注册状态、确认、重试、迁移及多电脑覆盖。
- protocol / relay 的注册保存回执、兼容处理和诊断。
- 受影响的 Android 注册链路兼容回归；不改变 Android 权限申请时机，不新增桌面推送实现。

本次不包含：更换 APNs 密钥、改变通知触发策略、重发历史任务通知、APNs 投递队列改造、后台常驻保活、自动开启系统权限。

**现场保护：实施与验证期间不得覆盖用户当前手机 App，不得擅自重启或部署生产 relay / 本机 daemon，不得向真实用户发送测试推送。** 在隔离环境和专用测试设备验证；生产发布与现场设备安装另行安排。若确需改 daemon，遵守根目录 AGENTS.md 的会话确认门和单实例规则。

## 2. 已知事实与尚未证明的判断

本轮只读排查观察到候选设备的 `push_platform`、`push_token`、`push_updated_at` 都为空，且存在 `has NO registered tokens` 日志。按当前数据库更新逻辑，正常登记后清空 token 会留下更新时间，因此该状态更符合尚未成功保存注册。

候选身份由新旧配对、设备公钥变化和活动时间综合推断，未通过用户 account 直接确认。本文不保存真实账号、设备 ID、IP、token 或原始日志，也不把候选推断写成已确认的用户根因。

当前源码中已发现的具体缺口：

| 环节 | 当前行为 | 风险 |
|---|---|---|
| APNs 注册启动 | `PushTokens.ensureStarted()` 首次调用后永久设置进程内 `started` | 失败后普通重连不重新请求 token |
| iOS 回前台恢复 | 刷新放在 `UIApplicationDelegate.applicationDidBecomeActive`，App 使用 SwiftUI Scene | Scene 生命周期下这个入口不能作为可靠的回前台恢复机制 |
| token 上报 | 发送前设置 `pushRegistered`，relay 路径没有持久化确认 | 排队／发送不能证明落库，失败可能被去重标记遮蔽 |
| 多电脑 | 辅助连接跳过注册，主连接承担注册 | 一个账号的 token 不能自动覆盖其他 daemon 账号 |
| 服务端保存 | `runCatching { setPushToken(...) }` 无明确回执 | 客户端无法区分保存成功、失败或未知 |
| 诊断 | 原生注册失败只记统一类别 | 无法区分授权、注册、上报、落库和确认的失败 |

这些缺口足以形成故障路径，但尚未证明用户此次命中了哪一个。当前源码与 App Store 已发布二进制是否一致也尚未核验。

当前首次通知授权通常由配对后 `Attached` 触发；不调整为首次打开 App 就弹窗。已授权用户冷启动时的静默 APNs 注册继续保留。互联网访问许可、本地网络权限、通知权限是不同状态，不依赖弹窗顺序推断注册成功。

## 3. 核心原则

1. 分开管理「系统通知权限」「取得当前 token」「各配对的服务端保存确认」。任一项成功不能代替其他项。
2. **不将 APNs token 持久化为客户端缓存。** 每次进程启动向系统获取当前 token；进程内可保留，用于本轮重试。relay 继续按现有方式保存投递所需 token。
3. 持久化的是待恢复状态、重试预算和确认摘要，不是“调用过一次就算成功”。
4. 获取 token 是设备级共享操作；上报确认是每个配对独立的操作。
5. 重试静默执行，不阻塞连接、聊天、发送提示词或切换电脑；不通过重复弹授权窗进行重试。
6. `confirmed` 仅表示 relay 已保存注册，不表示 APNs 已接受通知，更不表示手机已展示通知。

## 4. 状态与持久化

### 4.1 设备级状态

系统权限使用明确类别：`not_determined / denied / authorized / provisional / ephemeral / unknown`。App 内通知开关独立保存，不能将“App 开关开着”当成系统已授权。

token 获取状态：`idle / requesting / available / retry_wait / blocked`。一次系统注册在途期间合并其他触发，不并发启动多个相同请求。

持久记录版本、失败分类、失败轮数、下一次可重试时间；权限每次核对以系统实时结果为准。进程重建时不恢复为 `available`，必须重新获取系统 token。

### 4.2 按配对维护登记状态

状态键使用本地既有配对身份 `(relay, accountId, deviceId)`；这些身份只用于业务状态，不进入云端遥测。

| 状态 | 含义 |
|---|---|
| `pending` | 尚未确认当前期望登记状态 |
| `in_flight` | 当前请求已发起，等待回执 |
| `confirmed` | 当前期望状态已获服务端保存确认 |
| `retry_wait` | 暂时失败，等待下一次尝试／下一轮 |
| `blocked` | 权限、配对身份或协议等条件需要变化 |
| `legacy_unconfirmed` | 旧 relay 仅支持旧式发送，没有保存回执 |

持久摘要至少包含：schema 版本、期望启用／关闭、最后确认时间、失败类别、失败轮数、下次重试时间。短期 requestId、完整 token、在途 Future 不落盘。关闭 App 或杀进程后，原 `in_flight` 按待恢复处理，不算成功。

`confirmed` 不永久有效：

- 每次进程冷启动取得系统 token 后，为各有效配对重新确认一次；沿用持久失败冷却，避免崩溃重启形成重试风暴。
- token 更新、新配对、从设置开启权限／App 内通知开关开启，立即进入新一轮。
- 长时间运行的进程，最后确认超过 24 小时后，在下一次前台且连接可用时重新确认。
- 该机制提供最终恢复，不承诺后台即时发现服务端 token 被清除。

## 5. 获取 token 与有限重试

### 5.1 iOS 原生流程

- 首次权限仍在用户完成配对并进入可用连接流程后申请；多个配对共享一次权限请求。
- 已授权时调用 `registerForRemoteNotifications()`；成功回调更新进程内 token 并触发所有合法配对的登记。
- `.provisional` / `.ephemeral` 按系统允许的能力处理，不误判成拒绝。
- 失败回调记录安全错误类别，释放在途状态，进入重试；不再让一次性的 `started` 阻止恢复。
- 没有成功也没有失败回调时，使用 **30 秒前台有效等待时间**判为“尚未取得结果”，释放本次等待并纳入有限重试；不推断为权限拒绝或永久失败。
- 使用 SwiftUI `scenePhase` 或可靠的 UIApplication 生命周期通知接入前台恢复。不得继续依赖 Scene App 不调用的旧 delegate 回调。避免同时挂多套恢复监听导致重复请求。
- APNs 原生回调无 requestId；成功回调按系统当前 token 处理，结合当时权限／用户意图决定是否上报。迟到失败不能把已经取得有效 token 的状态回退为失败。

### 5.2 重试参数与触发

获取 token 与上报分别有预算，不能把两层重试嵌套放大成 3×3 次，也不能每次发送提示词新建独立重试任务。

| 参数 | 初始建议 |
|---|---|
| 一轮尝试次数 | 最多 3 次，包含首次请求 |
| 同轮重试等待 | 第一次失败后等待 5 秒，第二次失败后等待 30 秒，再各尝试一次 |
| 上报 ACK 等待 | 发往可用 socket 后 10 秒；排队等待不能冒充已发送 |
| 上报传输／单次短连接 | 沿用现有有界拨号与写超时；单次完整操作建议最多 30 秒 |
| 失败轮次冷却 | 5 分钟 → 15 分钟 → 60 分钟封顶 |
| 抖动 | 非首次重试加入小幅随机抖动，避免批量升级同时重试 |

触发点：启动、回前台、relay 连接恢复、观察到网络恢复、token 更新、新配对、权限／App 开关变化，以及发送提示词前的非阻塞检查。

普通触发只检查当前状态和冷却，不重置预算；新 token、新配对、权限由不允许变为允许、用户主动开启通知可以提前启动一轮。事件需要去重，网络抖动不能反复绕过冷却。

用户拒绝通知、App 开关关闭、身份撤销等不按瞬时网络失败循环重试。网络不可用时等待可用条件；配对身份被撤销时停止该配对注册，不替用户重新配对。后台不保活、不挂整点定时任务，挂起期间不计作前台超时，下一次进入前台后继续。

存储时间使用可校验时间戳，进程内耗时使用单调时钟；时钟回拨／时间戳损坏不得导致永久不重试，也不得清零失败预算制造高频重试。

## 6. 注册确认协议与 relay

建议采用增量扩展，名称可按现有协议规范调整，但以下语义必须保留：

1. `Attached` 新增带默认值的 `supportsPushRegistrationAck: Boolean = false`，由实际 relay 宣告能力。不能把本地直连生成的 `Attached` 当作 relay 支持证明。
2. 保留 `RegisterPush(platform, token)` 及原 wire 类型，新增可选 `requestId`，默认 null。新客户端只有在服务器声明支持时请求 ACK。
3. 新增 `PushRegistrationResult(requestId, result, code?)` 回执。`result` 至少区分 `stored / cleared / rejected / failed`；错误码为有限枚举，不返回原始异常、SQL 或 token。
4. relay 从**已认证 socket**确定 account/device，不接受请求任意指定其他设备。
5. 完成数据库事务且目标行实际存在／更新成功后才返回 `stored` 或 `cleared`；异常或身份不允许时返回明确结果。
6. 相同请求重复到达必须幂等；保存成功但回执丢失时，重试可再次 upsert 并返回成功。无需引入无限增长的请求历史表。
7. 只对带 requestId 的新请求返回新回执，避免旧客户端接收陌生 wire 类型。

### 并发、切换与关闭

- 同一配对仅保留一个有效登记任务，requestId 绑定当前 token 代际和用户启用意图；旧回执不得确认新 token、另一配对或更新后的关闭状态。
- 在途时 token 变化／用户关闭通知，废弃旧任务和排队旧帧，让最新期望状态最终获确认。
- 清空 token 也是需确认的操作；用户关闭通知后，迟到的 token 回调不得重新启用登记。
- 服务端也必须保证旧连接的登记不覆盖新连接的最新状态。结合 broker 的当前连接校验和按设备写入顺序实现，不能仅在客户端忽略旧 ACK。
- 拔掉配对或撤销凭据后停止任务；兼容现有联系人解绑清理，不留下无界后台任务。

### 普通连接与 LAN 短连接

- 普通 relay 控制面应在认证后即可处理注册及回执，不应依赖 daemon 在线或 E2E 握手完成；注册目标是 relay。
- 修复 `controlOutbox` 取出消息后发送失败丢失、以及发送前标记成功的问题。由状态机根据回执与超时决定重试，不再以 `Channel.send` 完成代替服务端保存。
- `RelayControlDial` 在新 relay 下发出注册后必须等待匹配回执再关闭；旧 relay 下保持原有 best-effort 行为。
- 每个配对优先复用现有已认证连接。LAN 补偿短连接不得与同设备的活跃 relay 连接相互顶掉；传输切换必须取消旧拨号并协调唯一通路。

### 新旧版本兼容

| 组合 | 行为 |
|---|---|
| 旧 App + 新 relay | 原注册报文照常处理，不强制新字段，不发陌生回执 |
| 新 App + 新 relay | 保存成功确认、有限重试与恢复全部启用 |
| 新 App + 旧 relay | 发送原兼容报文；标记 `legacy_unconfirmed`，不因缺 ACK 每 10 秒反复重试 |
| 新 App + 旧 daemon | 推送注册协议不依赖升级 daemon，正常工作 |

旧 relay 下实际拨号／发送失败仍可有限重试；发送完成仅代表已提交，不能展示服务端已确认。能力在每次真实 relay 连接重读，服务端升级后自动切换新模式。

## 7. 多电脑与身份范围

每个正常的 owner 配对分别登记同一个系统 token；多个账号注册不等于多个系统权限弹窗。不能继续假设主电脑账号可替其他账号接收通知。

联系人 inbox 沿用其允许的定向登记语义。headless bridge、guest、execution 等受限身份不得因本次修复获得额外推送权限；客户端与 relay 都保留现有权限判断。

多配对登记并发有界，建议最多 2 个上报任务；系统 token 获取始终只有一份。某个配对失败不拖住其他配对、不影响聊天。切换 UI 当前电脑不应丢失其他配对的恢复状态。

## 8. 存量用户迁移：必须交付

升级后首次运行，初始化新的恢复 schema，为所有既有有效配对创建待核对状态。旧“已经开始注册／已经上报”的判断不作为新确认依据。

| 旧状态 | 升级后的行为 |
|---|---|
| 系统已授权，从未取得 token | 无弹窗地重新向系统注册，并恢复失败重试 |
| 本地认为已上报，relay 实际为空 | 获取当前 token 后重新登记，取得保存确认 |
| token 曾失效被 relay 清除 | 用系统当前 token 重登记，不复用旧缓存 |
| 仅主电脑曾登记 | 自动补齐其他允许推送的配对 |
| 用户主动关闭 App 内通知 | 保留关闭意图；必要时补发清空登记并等待确认，不偷偷开启 |
| 系统已拒绝 | 展示设置入口，等待用户决定，不重复申请 |
| 系统尚未决定 | 维持原配对后申请时机，不把升级变成启动即弹窗 |
| 升级时离线／中途退出 | 保存未完成状态，下次继续，不能以“迁移运行过”跳过恢复 |

迁移必须幂等，只增加／修复推送状态，不清除配对、密钥、聊天、偏好或已有诊断预算。不把一次性的 migration version 当作每个配对已经恢复完成。

老用户在已授权、联网、配对有效的情况下，**不发送提示词也能自动恢复登记**。仍停留旧版且从未上报 token 的用户无法仅靠服务端补出 token，不宣称服务端发布已经修复所有用户。

## 9. 设置交互

在现有通知设置附近补充真实状态与必要操作，复用现有界面，不新增首次启动拦截页。

| 状态 | 展示与操作 |
|---|---|
| App 内关闭 | 显示关闭，保留原开关 |
| 尚未申请系统权限 | 用户开启时申请；不重复自动弹窗 |
| 系统拒绝 | 说明系统通知未开启，提供「前往设置」 |
| 系统允许，正在注册 | 「正在准备通知」；不暴露 token 等技术名词 |
| 多轮失败 | 「通知暂时无法完成设置」，提供「重试」 |
| 已确认登记 | 「通知已启用」，不写「推送已送达」 |
| 旧 relay 不支持确认 | 克制说明状态尚未确认；不要误报失败或显示新 relay 的成功状态 |

前往 iOS 通知设置优先用 `openNotificationSettingsURLString`，按最低系统版本与打开结果回退到 App 设置页。返回前台重新读取系统权限、恢复 token 获取与上报。

不新增独立「手动上传 token」按钮。异常状态的「重试」复用同一状态机，可提前启动一轮但应去重／防连点；不发送真实测试通知。正常状态不需要用户维护注册。

多电脑仅部分确认时显示部分完成，不能全局显示全部正常。UI 文案区分系统权限与 App 偏好，不把用户主动拒绝归类为产品故障。

任何同排小字／徽章遵守 AGENTS.md 的 `tightCenter` 规则。修改权限说明／首启流程前落实 [App Store 检查](../APP-STORE-REJECTIONS.md)。

## 10. 诊断：必须能判断卡在哪一层

复用现有 EP-28 推送诊断及 EP-29 生命周期边界，不另建绕过开关与预算的上传通道。

| 阶段 | 必须区分的结果 |
|---|---|
| 权限读取／申请 | 未询问、拒绝、允许、临时／静默授权、读取异常 |
| APNs 注册 | 开始、token 回调、失败类别、前台等待超时、迟到回调 |
| 登记提交 | 待发送、实际发送、传输失败、等待确认 |
| relay 保存 | 成功、清空、拒绝、数据库失败 |
| 回执与恢复 | 匹配确认、过期回执忽略、确认超时、重试耗尽、冷却、最终恢复、旧 relay 降级 |
| 实际通知投递 | 继续区分无目标、provider 接受／拒绝、传输失败、token 清理；不能并入登记成功率 |

允许字段：组件／版本／平台、真实推送环境类别、权限类别、触发原因、阶段、有限错误码、尝试次数、耗时、恢复结果。

原生错误仅通过经过允许表的 domain/code 映射为固定类别；不得直接采集 `NSError.description`、异常 message、原始响应或任意 domain 字符串。

云端不得上传 token（包括稳定哈希）、密钥、account/device/session 标识、通知标题正文或项目路径。业务状态里的身份与遥测严格分离；请求关联仅使用允许的短生命周期随机诊断 ID，不将 wire requestId 默认加入云端采集。

本地保留有界、安全的阶段结果供用户导出；relay 可沿用已有截断 account/device 的本地日志关联规则，不把身份带入云端。限制条数、大小与保留期，不落完整 token。云端继续服从用户开关、采样和现有预算；无云记录不等于没有发生故障。

## 12. 验收矩阵

以下都是待执行项目，不是本轮已完成验证。单元测试用于可控故障，原生回调与真实系统权限必须在专用 iPhone 上验证。

| 场景 | 必须满足的结果 |
|---|---|
| 新装 → 配对 → 允许通知 | 时机不提前；取得 token；relay 保存；客户端收到匹配 ACK |
| 首次注册断网，随后联网 | 不重装、不重配对，自动恢复；每轮不超过 3 次 |
| APNs 无成功／失败回调 | 前台超时可观察，有限重试；后台挂起不误判 |
| 拒绝 → 系统设置允许 → 回 App | 重新读取权限并恢复登记，无需杀进程 |
| 手机已获 token，上报途中断线 | 无虚假 confirmed；恢复后重新登记 |
| 服务端保存成功，但 ACK 丢失 | 幂等重试，最终确认，无重复副作用 |
| 首次 relay 认证成功，daemon 离线 | 注册可独立完成，不卡在 E2E 握手后 |
| token A 在途时更新为 B | A 的回执不能确认 B；服务端最终保存 B |
| 注册在途时关闭通知 | 最终清空获确认，迟到请求／回调不能重新启用 |
| 旧连接／新连接竞争 | 旧连接不能覆盖新意图；不会因补偿短连接互相顶掉 |
| LAN 直连 | 独立登记等待真实 relay ACK，聊天继续走 LAN |
| 多台电脑 + 联系人 inbox + 受限身份 | 合法配对各自恢复；受限身份不扩大权限 |
| 升级前已授权、已配对、relay token 为空 | 原地升级自动补齐，不要求重配对、手动按钮或发送提示词 |
| 升级前用户主动关通知 | 升级不打开通知，必要的撤登记可恢复 |
| 升级时离线／迁移中退出／反复冷启动 | 待恢复状态保留、迁移幂等、重试预算不被重置绕过 |
| 已 confirmed 后服务端丢失登记 | 下次冷启动／确认到期的前台核对可重新登记 |
| 新旧 App／relay／daemon 混用 | 符合第 6 节兼容表，未知 ACK 不冲击旧 App |
| 真实生产签名与开发签名测试包 | 环境正确；分别验证登记、APNs 接受与专用设备实际展示 |
| 日志隐私与遥测关闭 | 安全哨兵验证无 token／身份／内容泄漏，关闭采集不影响恢复 |
| 正常用户持续使用 | 不反复申请权限、不每条提示词发起注册、不持续耗电或刷日志 |

回归重点沿用并扩展 `PushRegisterTest`、`CollaboratorInboxPushTest`、relay `PushTest` / `CollaboratorPushTest`。新增测试必须注入真实故障边界，不只断言实现中赋过某个 Boolean。

协议变更按仓库规则跑完整受影响测试；合并前执行 `bash scripts/check-all.sh`（正确的本机 JDK 环境），iOS 构建及原生测试在 macOS / Xcode 上完成。Windows 测试不能冒充 iOS 编译或真机验收。提交前运行 `python scripts/check-repository-content.py` 与相应 diff 检查。

## 13. 发布与交付证据

用户审核本方案后，再进入实现。推荐先发布向后兼容的 relay，再发布客户端；客户端必须能处理 relay 回滚或旧的自托管 relay。新协议不得提高旧客户端最低要求。

生产操作安排前保留现有只读证据；不用更换密钥来“试试”，不清生产 token 或身份表。App Store 包签名检查、隐私文案、版本与提审遵循现有发布规则。

交付时分别提供：

1. 代码变更与兼容策略、重试参数及实际实现差异。
2. 验收矩阵逐项结果；未执行的真机项明确标记，不能以单测替代。
3. 一个旧版本异常状态升级后自动恢复的完整证据链：旧状态 → 系统 token 回调 → 上报 → relay 保存 → ACK。
4. 开发／生产通道的专用设备验证，区分“登记已确认”“APNs 已接受”“设备实际展示”。
