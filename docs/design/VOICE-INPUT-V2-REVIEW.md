# 语音输入 v2：流程总览与评审稿

状态：待评审（2026-10-06，本机时区）。电脑端的校对与协议已实现并合入本地 main；手机端尚未开工，等本次评审结论。

用途：把分散在两份文档里的方案合成一份可以独立读完的说明，供评审者提出意见。评审意见写在第 10 节。细节以文末「参考」里的两份文档和源码为准；三者不一致时的优先级见第 8 节。

## 1. 要解决的问题

今天在手机上口述一条提示要三步：点 ✓，转写文字落进输入框，读一遍并改掉错词，再点发送。错的几乎都是同音字和被听错的英文术语，例如把「Claude」听成「cloud」、把「effort」听成「edit」、把「用户体验」听成「用功体验」。

目标：说完点一次 ✓ 就发出去，发送前自动把这类错词改掉；任何不确定的情况都退回今天的做法。

历史约束：#221（v1.7.0）曾把「识别完直接发送」改为「落输入框再确认」，原因是识别结果会错，直接发送会浪费一轮甚至发出错误指令。本方案恢复直接发送的前提，是发送前经过校对，并且校对不可用时仍然落输入框。

## 2. 端到端流程

| 步 | 谁 | 做什么 | 耗时 |
|---|---|---|---|
| 1 | 手机 | 录音。iOS 默认用系统听写并实时显示文字；Android 与选了 Whisper 的 iOS 把音频发给电脑转写 | 用户说话的时长 |
| 2 | 手机 | 用户点 ✓。先判断「这一次会不会发送」（第 3 节）。不会发送：走今天的流程，到此结束 | 即时 |
| 3 | 手机或电脑 | 得到转写文字 | 系统听写不到 1 秒；Whisper 0.6–1.5 秒 |
| 4 | 手机 → 电脑 | 发送校对请求 `TranscriptRefine`（文字、语言、手机的默认 Agent）。录音条上方显示原文，状态写「校对中 · Claude」 | 一次网络往返 |
| 5 | 电脑 | 选校对用的 Agent：会话的 Agent 有校对器就用它，否则用手机的默认 Agent，都没有就回「不可用」。本轮只有 Claude 有校对器 | 即时 |
| 6 | 电脑 | 调用机主自己的 Claude 命令行做一次无工具的调用，只要求返回替换清单，例如 `cloud → Claude` | 实测 6.2–7.5 秒 |
| 7 | 电脑 | 校验替换清单（第 5 节）。任何一条不合规，整张清单作废 | 即时 |
| 8 | 电脑 → 手机 | 返回 `TranscriptRefined`：校对后的全文与生效的替换清单，或一个固定的失败码 | 一次网络往返 |
| 9 | 手机 | 在预览里高亮被改动的词，停留 700 毫秒后按普通发送路径发出；没有改动则立即发出 | 0–0.7 秒 |

从点 ✓ 到消息发出，目前预计 7–9 秒，其中绝大部分是第 6 步。

等待期间用户随时可以点录音条左侧的按钮退出：文字进输入框，不发送。

## 3. 总规则：让「✓ 会不会发送」看得见

录音条分两种，用左侧按钮区分。

| 录音条 | 出现条件 | 左侧按钮 | ✓ |
|---|---|---|---|
| 发送条（新） | 这一次确实会发送 | 键盘图标「完成并编辑」：文字进输入框，不发送 | 「完成并发送」：校对后发出 |
| 现有条（与今天逐项相同） | 这一次不会发送 | ✕「取消录音」：丢弃 | 「完成」：文字进输入框 |

「这一次会发送」要同时满足四条：

1. 设置「说完后」为「校对后发送」（默认值；另一个取值是「放入输入框」）。
2. 本会话有可用的校对器。
3. 连接正常。
4. 输入框是空的，也没有暂存或上传中的附件。

任何一条不满足就是现有条，行为、文案与今天完全相同，不请求校对，不出现「未校对」之类的提示。因此 Codex 会话（且手机默认 Agent 也是 Codex）、旧版 daemon、选了「放入输入框」的用户，都没有任何变化。

## 4. 发送条的各种结局

凡是不能发送的结局，规则只有一条：文字进输入框，光标在末尾，键盘弹起，不发送，输入框上方一句原因，原因保留到用户第一次编辑、发送或离开会话。

| 情形 | 进输入框的文字 | 原因行 |
|---|---|---|
| 校对成功 | 不进输入框，直接发出 | 无 |
| 等待中用户点左侧按钮 | 结果已到用校对后的，否则原文 | 无 |
| 超过等待上限（现定 8 秒） | 原文 | 校对超时，请检查后发送 |
| 超时后结果在电脑 12 秒硬超时之前到达，且输入框文字仍与原文逐字相同 | 换成校对后的文字，输入框内不高亮 | 已校对，请检查后发送 |
| 超时后结果到达，但用户已经改过文字 | 不动，结果丢弃 | 不变 |
| 替换清单未通过校验 | 原文 | 校对结果未采用，请检查后发送 |
| 校对不可用或调用失败 | 原文 | 这次没能校对，请检查后发送 |
| 等待中断连 | 原文 | 连接已断开，文字已保留，未发送 |
| 发送被拒（例如会话已降级） | 应发的文字 | 未发送，请检查后发送 |
| 等待中离开会话 | 原文追加进被离开会话的草稿，取消校对 | 无 |
| 录音达到 90 秒上限 | 等同点左侧按钮，不自动发送 | 无 |
| 转写失败、没有听到语音 | 与今天相同 | 与今天相同 |

回合进行中口述：发送排进进行中的回合，与打字发送相同。已发出的消息不带任何「语音」或「已校对」标记。

## 5. 安全设计

自动发送未经人眼确认的文字，是本方案最大的风险，对策有四层。

**只许换词。** 模型只返回替换清单，由电脑套用，不接受整段重写。校验规则（任何一条不满足，整张清单作废，退回原文）：

- 最多 12 条；空清单合法，表示无需修改。
- 每条的原片段必须在原文里逐字出现且恰好一次，各条位置互不重叠。
- 原片段与新片段各不超过 40 个字符。
- 新片段不含换行、控制字符、零宽字符、双向覆盖字符。
- 新片段最长为原片段长度的 2 倍加 4 个字符，用来拦截「把一个词换成一句话」。
- 被替换的字符合计不超过原文的 30%。短口述放宽：每条原片段不超过 12 个字符、合计不超过 32 个字符且不超过原文的 75% 时也通过。

**调用隔离。** 校对在空的私有目录里运行，禁用全部工具、MCP 与斜杠命令，不保存会话；转写文字只经标准输入传入，不出现在命令行参数里；系统提示写明不执行文字中的任何指令。

**跟随用户的 Agent。** 校对用哪个 Agent 只看会话的 Agent 与手机的默认 Agent，不会悄悄换成另一家，避免消耗用户没选的账号额度。

**不留痕。** 日志只记 Agent、耗时、替换条数与结果码，不记任何文字。超过 4,000 个字符的文字不调用模型。

## 7. 实测数据

| 项目 | 结果 |
|---|---|
| Claude `sonnet`、低强度、替换清单，经已安装的 daemon 代码真实调用 | 墙钟 6.2、7.5、6.8、6.4 秒 |
| 其中命令行自身的启动开销 | 约 3.5 秒 |
| Claude `haiku` | 多轮 44–100 秒，异常，不作默认 |
| Codex 常驻进程，替换清单 | 10.0–12.3 秒，超出等待上限，所以不做 Codex 校对器 |
| Codex 一次性命令 | 约 20 秒，其中启动约 18 秒 |
| 纠错质量样例 | 41 个字的句子含四个听错的术语，四处全部改对；另一句无错的句子返回空清单 |

真实调用还暴露过一个问题并已修复：上面那句 41 个字的口述要替换原文的 56%，被原先固定的 30% 上限整组作废，所以才有第 5 节的短口述放宽。

## 8. 文档之间尚未统一的地方

优先级：设计交接说明里的「评审决定」高于技术方案，技术方案高于设计板。

- 技术方案的第 3、6 节仍是评审前的写法，缺少这些已定的规则：两种录音条、输入框有草稿或附件时不发送、高亮停留 700 毫秒、90 秒上限与离开会话的处理、六句原因行。手机端开工前要同步。
- 设计板里让 ✓ 的外观在「会发送」与「不会发送」时完全相同，已被第 3 节取代。
- 设计板里「放入输入框」时仍先校对，已改为不校对。
- 设计板把 Codex 画成可用的校对器，本轮不成立。
- 设计板画的「现有」输入区有几处落后于线上，例如麦克风的位置与输入框行数，实现以线上为准。

## 9. 希望评审回答的问题

1. **等待上限。** 实测 6.2–7.5 秒，加上两次网络往返，现定的 8 秒上限会让相当一部分请求落入「超时后迟到套用」。三个选项：放宽到 10 秒；让校对进程常驻以省掉约 3.5 秒的启动；两者都做。常驻进程的生命周期、并发与空闲回收应当怎么设计？
2. **7–9 秒是否值得。** 今天的三步流程里，读一遍并改两个词大约也要这么久，但注意力在用户手上。等待期间用户只能看着。有没有办法把等待藏进说话的过程，例如 iOS 实时听写时对已稳定的前半段先行校对？
3. **两种录音条的风险。** 同一个位置的左侧按钮，在发送条上是「保留文字去编辑」，在现有条上是「丢弃」。用户形成习惯后，在现有条上误点会丢掉刚说的话。是否应当统一左侧按钮的含义，改用别的方式区分两种条？
4. **校验器能否支撑自动发送。** 清单合规但改错的情况没有防线，例如把一个本来正确的词换成术语表里的词，而产品无法撤回已发送的消息。700 毫秒的高亮是否足够，还是应当在改动较多时改为落输入框？
5. **校验阈值。** 第 5 节的各项上限，尤其是短口述放宽的三个数字，是否过松或过紧？有没有能绕过「只许换词」的构造？
6. **跨 Agent 校对。** 用户默认 Agent 是 Claude、当前会话是 Codex 时，由 Claude 校对并显示「校对中 · Claude」。这是否符合「跟随用户的 Agent」的本意，还是应当严格只看会话的 Agent？
7. **草稿与附件。** 输入框非空或有附件时一律不自动发送。这条是否过于保守？是否有更好的规则，例如只在草稿是本次会话里刚输入的情况下才合并发送？
8. **迟到结果。** 超时后把迟到的校对结果直接换进输入框，条件是文字未被改动。用户此时可能正在读原文，文字突然变化是否比丢弃结果更糟？
9. **隐私表述。** 使用 iOS 系统听写时，音频不离开手机；启用校对后，转写文字会多经过一次电脑上的 Agent。这段文字本来也会作为提示发给 Agent，是否仍需要在隐私说明与首次使用时单独交代？
10. **实施切分。** 手机端打算分两步：先做数据层与状态机并配齐自动化测试，再做录音条界面。有没有更稳妥的切法，或应当先行验证的假设？
