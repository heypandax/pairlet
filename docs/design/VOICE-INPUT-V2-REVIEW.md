# 语音输入 v2：流程总览与评审稿

状态：待评审（2026-10-06，本机时区）。电脑端的校对与协议已实现并合入本地 main；手机端尚未开工，等本次评审结论。

用途：把分散在两份文档里的方案合成一份可以独立读完的说明，供评审者提出意见。评审意见写在第 10 节。细节以文末「参考」里的两份文档和源码为准；三者不一致时的优先级见第 8 节。

## 1. 要解决的问题

今天在手机上口述一条提示要三步：点 ✓，转写文字落进输入框，读一遍并改掉错词，再点发送。错的几乎都是同音字和被听错的英文术语，例如把「Claude」听成「cloud」、把「effort」听成「edit」、把「用户体验」听成「用功体验」。

目标：说完点一次 ✓ 就发出去，发送前自动把这类错词改掉；任何不确定的情况都退回今天的做法。

历史约束：#221（v1.7.0）曾把「识别完直接发送」改为「落输入框再确认」，原因是识别结果会错，直接发送会浪费一轮甚至发出错误指令。本方案恢复直接发送的前提，是发送前经过校对，并且校对不可用时仍然落输入框。

## 2. 端到端流程

| 步 | 谁 | 做什么 | 耗时 |
|---|---|---|---|
| 1 | 手机 | 录音。iOS 默认用系统听写并实时显示文字；Android 与选了 Whisper 的 iOS 把音频发给电脑转写 | 用户说话的时长 |
| 2 | 手机 | 用户点 ✓。先判断「这一次会不会发送」（第 3 节）。不会发送：走今天的流程，到此结束 | 即时 |
| 3 | 手机或电脑 | 得到转写文字 | 系统听写不到 1 秒；Whisper 0.6–1.5 秒 |
| 4 | 手机 → 电脑 | 发送校对请求 `TranscriptRefine`（文字、语言、手机的默认 Agent）。录音条上方显示原文，状态写「校对中 · Claude」 | 一次网络往返 |
| 5 | 电脑 | 选校对用的 Agent：会话的 Agent 有校对器就用它，否则用手机的默认 Agent，都没有就回「不可用」。本轮只有 Claude 有校对器 | 即时 |
| 6 | 电脑 | 调用机主自己的 Claude 命令行做一次无工具的调用，只要求返回替换清单，例如 `cloud → Claude` | 实测 6.2–7.5 秒 |
| 7 | 电脑 | 校验替换清单（第 5 节）。任何一条不合规，整张清单作废 | 即时 |
| 8 | 电脑 → 手机 | 返回 `TranscriptRefined`：校对后的全文与生效的替换清单，或一个固定的失败码 | 一次网络往返 |
| 9 | 手机 | 在预览里高亮被改动的词，停留 700 毫秒后按普通发送路径发出；没有改动则立即发出 | 0–0.7 秒 |

从点 ✓ 到消息发出，目前预计 7–9 秒，其中绝大部分是第 6 步。

等待期间用户随时可以点录音条左侧的按钮退出：文字进输入框，不发送。

## 3. 总规则：让「✓ 会不会发送」看得见

录音条分两种，用左侧按钮区分。

| 录音条 | 出现条件 | 左侧按钮 | ✓ |
|---|---|---|---|
| 发送条（新） | 这一次确实会发送 | 键盘图标「完成并编辑」：文字进输入框，不发送 | 「完成并发送」：校对后发出 |
| 现有条（与今天逐项相同） | 这一次不会发送 | ✕「取消录音」：丢弃 | 「完成」：文字进输入框 |

「这一次会发送」要同时满足四条：

1. 设置「说完后」为「校对后发送」（默认值；另一个取值是「放入输入框」）。
2. 本会话有可用的校对器。
3. 连接正常。
4. 输入框是空的，也没有暂存或上传中的附件。

任何一条不满足就是现有条，行为、文案与今天完全相同，不请求校对，不出现「未校对」之类的提示。因此 Codex 会话（且手机默认 Agent 也是 Codex）、旧版 daemon、选了「放入输入框」的用户，都没有任何变化。

## 4. 发送条的各种结局

凡是不能发送的结局，规则只有一条：文字进输入框，光标在末尾，键盘弹起，不发送，输入框上方一句原因，原因保留到用户第一次编辑、发送或离开会话。

| 情形 | 进输入框的文字 | 原因行 |
|---|---|---|
| 校对成功 | 不进输入框，直接发出 | 无 |
| 等待中用户点左侧按钮 | 结果已到用校对后的，否则原文 | 无 |
| 超过等待上限（现定 8 秒） | 原文 | 校对超时，请检查后发送 |
| 超时后结果在电脑 12 秒硬超时之前到达，且输入框文字仍与原文逐字相同 | 换成校对后的文字，输入框内不高亮 | 已校对，请检查后发送 |
| 超时后结果到达，但用户已经改过文字 | 不动，结果丢弃 | 不变 |
| 替换清单未通过校验 | 原文 | 校对结果未采用，请检查后发送 |
| 校对不可用或调用失败 | 原文 | 这次没能校对，请检查后发送 |
| 等待中断连 | 原文 | 连接已断开，文字已保留，未发送 |
| 发送被拒（例如会话已降级） | 应发的文字 | 未发送，请检查后发送 |
| 等待中离开会话 | 原文追加进被离开会话的草稿，取消校对 | 无 |
| 录音达到 90 秒上限 | 等同点左侧按钮，不自动发送 | 无 |
| 转写失败、没有听到语音 | 与今天相同 | 与今天相同 |

回合进行中口述：发送排进进行中的回合，与打字发送相同。已发出的消息不带任何「语音」或「已校对」标记。

## 5. 安全设计

自动发送未经人眼确认的文字，是本方案最大的风险，对策有四层。

**只许换词。** 模型只返回替换清单，由电脑套用，不接受整段重写。校验规则（任何一条不满足，整张清单作废，退回原文）：

- 最多 12 条；空清单合法，表示无需修改。
- 每条的原片段必须在原文里逐字出现且恰好一次，各条位置互不重叠。
- 原片段与新片段各不超过 40 个字符。
- 新片段不含换行、控制字符、零宽字符、双向覆盖字符。
- 新片段最长为原片段长度的 2 倍加 4 个字符，用来拦截「把一个词换成一句话」。
- 被替换的字符合计不超过原文的 30%。短口述放宽：每条原片段不超过 12 个字符、合计不超过 32 个字符且不超过原文的 75% 时也通过。

**调用隔离。** 校对在空的私有目录里运行，禁用全部工具、MCP 与斜杠命令，不保存会话；转写文字只经标准输入传入，不出现在命令行参数里；系统提示写明不执行文字中的任何指令。

**跟随用户的 Agent。** 校对用哪个 Agent 只看会话的 Agent 与手机的默认 Agent，不会悄悄换成另一家，避免消耗用户没选的账号额度。

**不留痕。** 日志只记 Agent、耗时、替换条数与结果码，不记任何文字。超过 4,000 个字符的文字不调用模型。

## 8. 文档之间尚未统一的地方

优先级：设计交接说明里的「评审决定」高于技术方案，技术方案高于设计板。

- 技术方案的第 3、6 节仍是评审前的写法，缺少这些已定的规则：两种录音条、输入框有草稿或附件时不发送、高亮停留 700 毫秒、90 秒上限与离开会话的处理、六句原因行。手机端开工前要同步。
- 设计板里让 ✓ 的外观在「会发送」与「不会发送」时完全相同，已被第 3 节取代。
- 设计板里「放入输入框」时仍先校对，已改为不校对。
- 设计板把 Codex 画成可用的校对器，本轮不成立。
- 设计板画的「现有」输入区有几处落后于线上，例如麦克风的位置与输入框行数，实现以线上为准。

## 9. 希望评审回答的问题

1. **等待上限。** 实测 6.2–7.5 秒，加上两次网络往返，现定的 8 秒上限会让相当一部分请求落入「超时后迟到套用」。三个选项：放宽到 10 秒；让校对进程常驻以省掉约 3.5 秒的启动；两者都做。常驻进程的生命周期、并发与空闲回收应当怎么设计？
2. **7–9 秒是否值得。** 今天的三步流程里，读一遍并改两个词大约也要这么久，但注意力在用户手上。等待期间用户只能看着。有没有办法把等待藏进说话的过程，例如 iOS 实时听写时对已稳定的前半段先行校对？
3. **两种录音条的风险。** 同一个位置的左侧按钮，在发送条上是「保留文字去编辑」，在现有条上是「丢弃」。用户形成习惯后，在现有条上误点会丢掉刚说的话。是否应当统一左侧按钮的含义，改用别的方式区分两种条？
4. **校验器能否支撑自动发送。** 清单合规但改错的情况没有防线，例如把一个本来正确的词换成术语表里的词，而产品无法撤回已发送的消息。700 毫秒的高亮是否足够，还是应当在改动较多时改为落输入框？
5. **校验阈值。** 第 5 节的各项上限，尤其是短口述放宽的三个数字，是否过松或过紧？有没有能绕过「只许换词」的构造？
6. **跨 Agent 校对。** 用户默认 Agent 是 Claude、当前会话是 Codex 时，由 Claude 校对并显示「校对中 · Claude」。这是否符合「跟随用户的 Agent」的本意，还是应当严格只看会话的 Agent？
7. **草稿与附件。** 输入框非空或有附件时一律不自动发送。这条是否过于保守？是否有更好的规则，例如只在草稿是本次会话里刚输入的情况下才合并发送？
8. **迟到结果。** 超时后把迟到的校对结果直接换进输入框，条件是文字未被改动。用户此时可能正在读原文，文字突然变化是否比丢弃结果更糟？
9. **隐私表述。** 使用 iOS 系统听写时，音频不离开手机；启用校对后，转写文字会多经过一次电脑上的 Agent。这段文字本来也会作为提示发给 Agent，是否仍需要在隐私说明与首次使用时单独交代？
10. **实施切分。** 手机端打算分两步：先做数据层与状态机并配齐自动化测试，再做录音条界面。有没有更稳妥的切法，或应当先行验证的假设？

## 10. 评审意见

评审日期：2026-10-06（America/Los_Angeles）。已读本文全文，核对技术方案、交接说明及其「评审决定」、相关 daemon／协议／手机源码和现有测试；未重新操作在线设计板，未调用真实模型或做真机实网验证。下文是本次评审建议，不把建议视作已经替换第 3–8 节的产品决定。

**结论：可以继续做受控验证，当前证据不足以批准默认开启自动发送。** 替换清单、整组拒绝、无工具调用和失败回落都有价值，但校验通过只说明格式受限，不能证明文字保持了用户原意。上线前应先解决自动发送授权、语义误改、草稿与发送归属、新增数据路径披露四类问题。以下 P1 指启用自动发送前必须解决，P2 指实施／对外验收前补齐，P3 指后续优化。

### 按第 9 节逐条回应

**1. 等待上限：先采用 10 秒作为实验预算，常驻另做可行性验证，不建议两者一起进入首轮手机实现。（P2）**

- 四次 6.2–7.5 秒的本机调用只能说明这条路径有希望，不能估计超时比例，更不能作为移动网络的 p95。应分别记录点 ✓ 到最终转写、转写到校对返回、展示停留、发送到回执的耗时；Whisper 路径还要包含音频上传。手机校对预算从最终转写就绪起算，包含校对请求排队和往返；这里的一次请求／响应是一轮往返，不能把各阶段的往返重复累计。
- 10 秒可给现有一次性调用更多余量，但它不是「✓ 后 10 秒内必发」承诺。手机用单调时钟维护本地截止时间；daemon 的 12 秒从自己的处理阶段起算，两端起点不同，不能把 `12 − 8` 当成手机精确的迟到窗口。源码的模型前准备、协作式取消和进程清理也意味着 `timeout` 回包未必恰在手机第 12 秒到达。客户端必须独立收束状态，不依赖收到硬超时回包。
- 若继续研究常驻，先用假数据探针验证：多次请求能否不带前次文本、每次重新绑定术语表与配置、保持禁工具／禁 MCP／不保存会话、取消后下一请求不收旧输出。向同一个 stream-json 会话不断追加输入会积累历史，不能未经验证就用于不同会话的校对。
- 生命周期建议：有明确启用意图后懒启动；先限制 daemon 全局一个执行槽，排队时间算进预算，过期直接回落；同一次录音的新版本替代旧版本，其他设备不应互相抢占。空闲回收可先试 5 分钟，再按内存与延迟实测调整；账号、预设、模型或 CLI 版本变化时回收重建，daemon 退出时清理进程树。没有请求隔离证据时继续用一次性调用，不承诺一定能省下全部启动耗时。

**2. 7–9 秒是否值得：可能减少操作，但尚未证明能减少用户负担；本轮不做前缀预校对。（P2，前缀预校对为 P3）**

收益应是「少一次检查／点击且错误不增加」，不能只比较墙钟时间。等待能随时转为编辑、过程可理解，比把同样的等待隐藏起来更重要。先用人工构造或明确授权的样本比较手动流程与新流程的完成时间、误改、回落和主动转编辑情况，保留「放入输入框」作为直接路径。

iOS 的 `stablePrefix()` 只取相邻两次识别假设的公共前缀，属于显示启发式，不代表识别器承诺不再修订。后半句也会改变前半句含义，例如「不是 cloud，是 Claude」。预校对会引入版本失配、重复费用，以及用户尚未点 ✓ 时就向模型提供方发送文本的新数据路径。若以后试做，必须绑定录音与转写版本，最终文本不一致就作废，不能拼接不同版本的替换；还要测预请求是否反而占住最终请求的执行槽。预热进程可以单独验证，不需要先上传口述文本。

**3. 两种录音条：赞成统一左侧为「结束并编辑」，发送意图由右侧按钮自身表达。（P1）**

当前设计让同一位置在不同会话、连接或附件状态下分别保留与丢弃内容，误触后果不对称；只观察左侧小图标才能推断右侧 ✓ 的行为，也不够直接。建议左侧始终保留文字；右侧用可见的发送／完成差异并配套无障碍名称，不只改朗读标签。转写尚未结束时，左侧应立即锁定「完成后编辑」意图，再等转写，不假装此刻已有全文。

这会改变现有条的取消语义，与第 3 节「完全相同」冲突，需要明确采纳后再改规格。若暂不接受统一，则至少在单次录音内冻结左侧语义：不能因断连把键盘按钮原位变成丢弃按钮；重新连上、附件消失或能力恢复，也不能把已经展示为「完成」的本次录音自动升级为发送。启动时确定展示模式，点 ✓ 时记录用户意图，发送前再检查资格；后续条件变化只允许降为编辑。320pt、200% 字号和读屏下都应验证右侧动作可辨认。

**4. 校验器能否支撑自动发送：不能独立承担这项保证，700 毫秒只能作反馈动画。（P1）**

现有校验器不检查否定、动作、对象、数值或语义。即使一字未改，空清单也只表示模型没提出修正，不等于转写准确；漏掉的「不」不会因返回空清单而恢复。下文第 5 条给出了当前实现接受的语义翻转反例。工具禁用保护的是校对进程，修改后的文字一旦送入正常 Agent，会重新进入有工具能力的执行路径。

建议保留存量用户的「放入输入框」行为，自动发送先作为明确选择后的受控功能；设置说明应交代校对仍可能出错，不应把默认开关迁移当成用户已授权新行为。改动较多时确实应回落：至少把「依赖短口述放宽才通过」的结果先纳入人工检查，再用独立样本决定是否放宽。但只按改动比例分流仍挡不住低比例的语义翻转；否定、数量、路径、命令、动作／对象变化要有额外保守规则，规则未能判断时回落。模型自报的置信度也不足以替代这一判断。

预览最多六行且停在末尾，前部改动可能根本不在屏内；读屏也无法在 700 毫秒内读完多处替换。因此不能在安全论证里把这段停留算作人工确认，也不能用「用户没按编辑」表示认可。即使将来有了更多质量数据，自动发送仍需保留这一风险边界。

**5. 校验阈值：结构限制可保留，但短口述放宽与逐条增长上限目前过松，不能叫作「只许换词」的保证。（P1）**

直接用 JShell 调用工作区已有的 `TranscriptEditValidator` 编译类复核，以下四组均返回 `Accepted`；未运行模型，结果与当前源码规则一致：

| 原文 | 替换 | 实际结果与原因 |
|---|---|---|
| `不要删除这个目录` | `不要 → ""` | 得到 `删除这个目录`。删除两个字只占 25%；`to` 允许空串，普通 30% 规则已经放行 |
| `请检查这个文件` | `检查 → 删除` | 得到 `请删除这个文件`。等长替换只占 2/7，无需短口述放宽 |
| `请检查日志` | `日志 → 日志并删库` | 得到 `请检查日志并删库`。新片段 5 字，不超过 `2 × 2 + 4 = 8`；40% 触及比例通过短口述规则 |
| `abcdefghijklmnop` | 把 `a` 到 `l` 分别换成相应大写字母重复六次，共 12 条 | 16 字扩成 76 字。每条原片段 1 字、合计 12 字、占 75%，全部合法；每条都拿到 4 字增长余量，累计扩写没有总量限制 |

这些是校验边界反例，不是模型实际输出这些内容的概率证据。它们足以否定「合规就不会追加或改变指令」的结论，也说明单纯把 75% 降回 30% 无法解决根本问题。

建议把「可展示的建议」和「可自动发送」分开判断：空目标／纯空白目标、否定或动作变化、命令／路径／数值变化先回落；增加全文总增长约束，覆盖多条相邻替换拼成一句话的情况，并在应用后重检总长度。只删除 `to == ""` 的漏洞仍不够，第二个反例完全等长。12 条、40 字可作为资源与格式限制；12／32／75 只是为一个样本调整出的经验值，不能据此确立安全阈值。

同时保留正例：多次出现的 `cloud` 因唯一匹配规则无法直接替换，纯术语短句可能触及 100%，这些拒绝未必应继续放宽；落输入框是合理结果。质量样本应覆盖无错原文、正常的 `cloud`／`edit`、重复术语、中英混说、否定和数值，而不只重复已有四处纠错样本。长度单位应统一写为 UTF-16 code unit；源码并非按用户看到的字形计数，代理对完整也不等于组合字形边界完整。

**6. 跨 Agent 校对：本轮优先建议严格跟随会话 Agent；默认 Agent 不足以代表用户同意这次跨服务传输。（P1）**

用户选择 Codex 会话，可能就是要使用该会话的模型服务或数据边界。手机默认 Claude 只说明新建会话的偏好，不能推导出已有 Codex 会话也允许先把原文交给 Claude；发送后才显示「校对中 · Claude」尤其不能承担事前告知。若决定保留既定回退规则，应在启用时明确说明并由用户选择，且在点 ✓ 前能看见本次校对器；不应再把这一规则概括为「不会换成另一家」。

还要区分 CLI 品牌和实际模型提供方：`ClaudeRuntime` 会应用用户预设／网关，`ClaudeTranscriptRefiner.modelArgs()` 在该路径通常不传 `sonnet`，延迟、额度和接收方都可能不同。当前 `isAvailable()` 只检查可执行文件及 Windows shim，并不验证登录、额度、模型或网关可用性。因此能力字段表示「存在可尝试的适配器」，不能承诺「这一次确实会发送」，也不能据此展示「未登录」等未经探测的原因。按现有协议显示一般失败并回落即可；会话 Agent、默认 Agent、连接或配置变更后不要沿用过期的发送资格。

**7. 草稿与附件：保留当前保守规则，不采用「最近输入就合并发送」。（P1）**

输入时间无法表达发送意图：刚写的也可能是待核对的命令，旧草稿也可能仍有用。附件检查应覆盖待选取、压缩、上传、失败和已经落盘但仍暂存的状态；存在任何内容都走编辑路径。资格应读取当前 composer 的实时文本和 IME 状态，而不是有 400 毫秒保存延迟的持久化草稿。

必须在点 ✓ 和真正提交发送前各核对一次；等待期间新增草稿、选图回调或上传完成都可能改变状态。`sendPrompt(text)` 默认会带上当时的附件并清空暂存列表，不能只在开始录音时检查一次就直接调用。发现变化后，把本次文字追加到正确草稿，保留已有内容与附件，不自动合并发送；本次一旦选择编辑，也不能因草稿后来被清空而恢复自动发送。

**8. 迟到结果：建议本轮超时后直接忽略，不自动替换输入框。（P1）**

「逐字相同」不等于「用户没动过」：用户可以编辑后撤销、只移动光标或选中片段、正在用 IME 组合输入，也可能已经读完准备点击发送。无高亮地换字会在最后一刻改变用户确认的对象。超时是一个清楚的交接点：恢复原文供编辑，撤销自动发送资格，尽力取消校对，忽略已经在途的结果。取消只是减少后续工作，不能撤回模型已经收到的内容。

如果迟到结果的价值以后被证明值得增加交互，可提供用户主动采用的建议。应用前应检查录音 ID、会话／电脑身份、草稿修订号及输入状态；任何编辑、手动发送、新录音、离开页面或超时都应使旧操作失效。保留当前自动替换方案时，这些保护仍需补齐，但它们只能减少竞态，不能解决用户正在阅读时的突变问题。

**9. 隐私表述：需要补充，而且问题中的「iOS 音频不离开手机」应先纠正。（P1）**

`NativeDictation.ios.kt` 创建识别请求时未设置 `requiresOnDeviceRecognition`，也未用 `supportsOnDeviceRecognition` 作为强制本地识别条件。Apple 文档说明，防止音频经网络发送需设置相应属性且设备支持；当前代码只能说使用 Apple Speech，不能保证始终端侧处理。这也是仓库 [App Store 拒审记录 R4](../APP-STORE-REJECTIONS.md) 已经明确纠正过的表述。[Apple：requiresOnDeviceRecognition](https://developer.apple.com/documentation/speech/sfspeechrecognitionrequest/requiresondevicerecognition)、[supportsOnDeviceRecognition](https://developer.apple.com/documentation/speech/sfspeechrecognizer/supportsondevicerecognition)。

校对新增的是「最终发送前，把原始转写及项目术语交给电脑上 CLI 配置的模型服务」。用户最终可能选择编辑、取消或根本不发送，接收方还可能与当前会话不同，故不能用「反正之后会发给 Agent」代替披露。应说明手机到电脑的 E2E 传输与电脑到模型服务是两段路径，列明所发内容、用途、配置所决定的接收方、额度使用，以及关闭校对的方法。Apple 当前 5.1.2(i) 要求披露向第三方 AI 分享个人数据并在分享前取得明确许可；首次启用的说明与选择可承担此事，不必每次弹窗，但存量首启同意不能未经核对就视为覆盖新增用途。[App Review Guidelines 5.1.2(i)](https://developer.apple.com/app-store/review/guidelines/#data-use-and-sharing)。

产品内披露、隐私政策、审核备注和 ASC 隐私填报应按真实路径一致复核。「不留痕」仅能承诺本组件已验证的日志与会话持久化行为；禁用 CLI 会话保存不代表模型提供方或自配网关不保留数据。项目术语也属于传出内容，详见补充风险 A5。

**10. 实施切分：保留状态机先行，但先定契约，再做可关闭的小范围完整流程；无障碍和隐私不能最后才补。（P2，授权与终态约束为 P1）**

建议顺序如下，均为后续实施建议，本次不执行：

1. **先固定决策与不变量。** 明确默认值及升级行为、左侧语义、跨 Agent、超时终态、后台／离开处理和发送提交边界；先跑第 5 条反例与人工标注质量样本，再测目标网络、长短口述、CLI 登录／预设／额度失败下的耗时。四次本机成功调用不作为上线门槛的替代。
2. **状态机与宿主接口一起做。** 用假时钟、假校对器和假发送器覆盖重复回包、乱序、截止时间两侧、双击、编辑、自然 Final、90 秒上限、前后台、切会话／电脑、草稿更新、附件回调、发送拒绝及回执未知。明确每次录音只选择一次终局去向，校对结果不能直接调用面向当前会话的裸发送入口。按状态机事件测试，不靠真实等待 8／10／12 秒。
3. **接一条可人工验收的完整路径。** 在内部开关下先把成功结果交给用户检查，以便观察误改与真实等待；这一测试模式不改变正式「放入输入框」选项不调用校对的约定。接着在明确选择自动发送的测试用户上验证该路径，同时交付可见动作、退出入口、读屏语义和数据披露。
4. **覆盖第二种引擎与混合版本后再扩大范围。** iOS 原生与 Whisper 的 capture 生命周期不同，必须分别验收；旧 daemon、新旧客户端、桌面共享数据层、多设备、断连后的 prompt 回执都要走通。真机验收应同时观察原文是否保住、是否重复发送、焦点／键盘／光标是否正确，不只看成功气泡。

埋点保留无文本的固定枚举与耗时分桶，但 `applied` 只能表示采用了替换，不能当作「纠错正确率」；`voice_sent` 也要明确是本地提交还是 daemon 确认。质量靠有明确预期的测试样本和自愿反馈判断，不采集用户口述来填补证据不足。技术方案里的「≤6 秒」验收与本文 7–9 秒、拟议 10 秒预算不一致，应在实施前统一口径。

### 未列出的风险

**A1. 非点击事件可能意外变成发送授权。（P1）**

当前 `onNativeFinal()` 直接调用 `deliverTranscript()`，而原生识别器的 Final 回调与用户点击 ✓ 是两个独立事件；`beginTicker()` 到 90 秒也直接调用 `stopVoice()`。若仅把 `deliverTranscript()` 改成「条件满足就校对并发送」，识别器自行结束、计时上限、重试结果都会继承发送行为。应单独记录本次用户明确选择的完成动作；自然 Final、音频中断、达到上限、失去前台与锁屏都不能产生新的自动发送授权。退到后台后即使计时器恢复、结果到达，也不能突然发送；待已授权发送提交之后则由现有发送恢复机制负责，不能再制造草稿副本。

**A2. 「校对完成」「本地提交」「daemon 收到」之间缺少明确分界。（P1）**

`sendPrompt()` 创建 `promptId`、添加待发送气泡，并异步发送帧后就返回 `true`；现有 outbox 会跨重连缓冲，返回值不代表送达。只有尚未提交发送或返回 `false` 时，才能走「未发送，恢复草稿」。一旦进入发送路径，即使断连或丢回执，也应继续沿用同一 `promptId` 的恢复和确认，不能又落一份可手动发送的副本，否则用户点击发送会产生新 ID、执行两次。重复 `TranscriptRefined` 和 700 毫秒结束／编辑点击竞态也必须经过一次性的提交门；提交后不能再承诺左侧按钮会取消已交出的消息。第 4 节的「等待中断连」应明确仅指发送提交前。

**A3. 保存到被离开会话的草稿不是现有 `pendingVoiceText` 能直接完成的。（P1）**

该字段目前只有一个 `String?`，`App.kt` 在消费时把它追加到当时的 composer；`abandonVoice()` 则清空录音。新流程要跨离开／断连保存，必须绑定发起电脑、稳定会话身份、录音 ID、composer 世代和草稿版本，并与 `composerKey()` 的会话 ID 迁移规则协调，不能在回调里现读当前会话。原生听写目前还没有像 Whisper 上传那样生成 captureId，需要在录音开始时建立统一身份。保存应追加且只做一次，并防止页面里延迟 400 毫秒的旧草稿写回覆盖刚保存的文字；A → B → A、新会话首次取得 sessionId、切电脑及后台回包均应有用例。

**A4. 每会话一个任务不等于全局限流或完成后去重。（P2）**

`TranscriptRefineService` 的运行表按 `convoId` 分组：同会话的新请求会顶掉其他设备的请求，不同会话则可各启动一个 CLI；完全相同的重发只在任务运行期间共享，完成后运行表即删除，再次投递会重新调用模型。若客户端沿用普通 outbox 重连重发，可能重复花额度；`AudioCancel` 只取消当前运行项，也不能阻止稍后才到达的旧请求。首轮就应明确离开／超时后待发请求的失效规则和客户端忽略旧结果的条件，并给 daemon 设全局并发／有界排队。若保留重试，再补按请求身份的短期结果复用或取消记录，说明内存中的文本保留时间；不能把 `TranscribeService` 已有的去重能力当成校对服务也已具备。无需为此扩大成通用任务平台。

**A5. 术语表既是数据传出面，也可能影响模型指令。（P1）**

`ProjectTerms` 读取目录名、分支和顶层文件名，`RefineGlossary` 仅限制长度／可打印字符，然后 `RefineContract.systemPrompt()` 把它们直接拼入系统提示。合法文件名仍可包含类似「忽略前面要求」的自然语言，长度和字符过滤无法赋予其可信度。当前 `--system-prompt` 又把包含这些术语的内容放在 argv，因此「原始转写不在命令行」成立，但不能推导出「项目相关文本均不在命令行」或「校对不知道项目文件信息」。建议将术语作为有明确边界的不可信数据传入，固定系统指令并约束可接受候选；审查进程参数与 CLI 自身日志的暴露。空目录和无工具不能消除模型因这些输入产生错误替换的风险，仍需第 4／5 条的发送保护。

**A6. 手机数据层的自动发送会影响共享它的宿主。（P1）**

技术方案写「桌面数据层自然受益，UI 另议」，但如果共享 `PocketRepository` 在收到结果后自动发送，未适配新录音条的宿主可能没有可见等待、退出入口或设置。应由已完成交互与披露的宿主显式启用自动发送；桌面范围外就保持既有行为。新客户端每个连接还需正确声明 `ClientCaps.supportsTranscriptRefine`，并按当前 daemon 的能力选择具体可用 Agent，而非仅判断列表非空。协议可解码、daemon 宣告适配器、UI 完成可控的发送流程，是三项独立验收条件。

**A7. 「等待时保留原文」尚未覆盖根本没有最终转写的阶段。（P2）**

Android／Whisper 在上传或转写期间没有原文；iOS 等 Final 时只有可能继续修订的假设。此时点编辑、断连或离开会话，不能执行一句「原文进输入框」就算完成。应补阶段表：有最终文字时立即保存；只有 iOS 部分文字时保留并标明尚未完成识别；只有音频时说明是否保留本次音频供重试、如何归属原会话及何时清理。本轮至少不能显示「文字已保留」而实际调用 `clearVoice()` 丢掉唯一音频。无需默认持久保存所有录音，但承诺和实现必须一致。

**A8. 高亮位置不能靠在返回全文里搜索 `to`。（P2）**

协议只保证 `from` 在原文唯一，不保证 `to` 在结果唯一。例：`请比较 cloud 和 Claude 的输出` 中 `cloud → Claude` 后有两个 `Claude`；后续替换也可能改变前面片段的位置。应根据原文中的有序区间累计长度差计算展示范围，核对得到的全文与 daemon `text` 一致，发送仍以 daemon 的全文为准；匹配或边界不一致时回落，不猜位置。多替换、相同目标词、emoji／组合字形和屏外改动都要覆盖。高亮正确是解释改动的前提，但仍不构成人工确认。

## 11. 对评审意见的处理（2026-10-06）

第 10 节引用的源码事实已逐条核对，全部属实；四组校验反例按 `TranscriptEditValidator.check` 的规则推演都会通过。本节与第 3–5 节冲突时以本节为准；标「待用户确认」的两项在确认前不进入实现。

### 已定

| 评审项 | 决定 |
|---|---|
| 1 等待上限 | 手机端上限改为 10 秒，从最终转写就绪起算，手机用单调时钟自行收束，不依赖 daemon 的超时回包。常驻进程不进本轮 |
| 2 前缀预校对 | 不做 |

### 两级校验

起因：只有一级时，任何一条不合格就整组作废。用真实命令行跑过的口述「帮我看下 cloud code 的 demon 日志，把 edit 调到最低，优化一下用功体验」会因为「用功体验 → 用户体验」读音不近而四处全部不改，比今天还差。

**整组作废**（原文落输入框）：现有结构规则，加上全部替换的净增长超过 `12 + 原文长度 / 5`。

**单条丢弃**（其余照常套用，不自动发送）：

- 新片段为空或纯空白；
- 新旧片段里的数字与中文数词不一致；
- 新旧片段里的否定词数量不一致；
- 新旧片段里的路径或命令符号不一致。

**套用但不自动发送**：

- 这条替换不属于以下任何一种：只改大小写或空格；新片段是术语表里的词；中文换等长中文且逐字同音或近音（平翘舌、前后鼻音、n/l、f/h）；
- 新片段引入了原片段没有的高危动词（删、清空、覆盖、重置、delete、reset、force 等）。例如同音且改对了的「山 → 删」也交给用户确认。

**自动发送**：没有丢弃，且每条都通过上面两项。空清单照旧可以发送。

已知代价：术语表规则仍允许把一个正确的词换成术语表里的名词，后果限于名词被换错。daemon 日志只记套用、丢弃的条数与是否授权，用来判断规则松紧。

### 手机端状态机的不变量

- 只有用户点「完成并发送」才产生发送授权；识别器自行结束、90 秒上限、退到后台、重试结果都不产生授权。
- 每次录音最多提交一次发送。提交之后断连或丢回执沿用同一个 `promptId` 的恢复，不再落草稿；只有提交被拒才把应发的文字落输入框。
- 点编辑、超时、断连、离开会话、退到后台、输入框或附件出现内容，任何一项发生在提交之前，本次录音永久降为编辑，之后到达的校对结果丢弃。
- 落草稿的目标是录音开始时的电脑与会话，不是回调时的当前会话。
- 离开会话时：已有最终文字或 iOS 的部分文字，追加进原会话草稿；只有音频（Whisper 在途）时取消并丢弃，与今天相同，不显示「已保留」。
- 校对结果没有 `autoSend` 授权时不发送，校对后的文字落输入框。
- 高亮区间由原文与有序替换清单推算，推算出的全文必须与 daemon 返回的全文一致，否则按「校对结果未采用」处理。

### 待用户确认

1. **默认值。** 建议存量与新用户都默认「放入输入框」，自动发送主动开启，开启时完成说明与同意。
2. **左侧按钮。** 建议所有录音条左侧统一为「保留文字去编辑」，发送与否由右侧按钮的外观区分；这会改掉今天 ✕ 的丢弃行为。

这两项定下后，再补一轮只含「右侧按钮外观」和「首次启用说明页」的设计稿。

### 实施顺序

1. daemon：闸门、术语表改走标准输入、全局执行槽、Agent 选择规则。完成后用真实命令行再验一次（输入格式变了）。
2. 手机端状态机与假时钟测试，先不接界面。
3. 上面两项待确认定下后：设计稿、界面、设置项、披露、真机验收。
