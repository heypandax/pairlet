协议实现遵守主方案的可选字段、默认值和 capability 协商。旧 App/新 daemon、新 App/旧 daemon、旧 relay 均有兼容用例；旧端缺少历史完成信号时保留部分覆盖，不将“没收到历史”直接判错。wire 与涉及鉴权/E2E 的变更分别完成兼容和安全专项评审。

历史诊断期限沿用场景稿中的 **15 秒初始提案**，在新双方具备能力时生效，并通过受控样本校准；它只产生诊断，不重发创建请求、不终止 Agent、不清空历史。正常排队、人工等待、后台挂起和取消分别处理。

**B 的代表性验收场景**：

| 场景 | 后台应能回答 | 正常对照 |
|---|---|---|
| 同项目三份历史，一份读取失败 | 扫描总数、失败数、返回数、部分结果及读取失败阶段 | 无合法消息导致的空列表不报读取异常 |
| 大历史在读取、编码、传输或应用处失败 | 最后成功阶段、规模、对应端的诊断证据和缺失证据 | 正常大历史、合法截断不产生同类错误 |
| 已收到 live，但历史未完成 | 区分未收到、收到未合并、完成标记缺失、尚未布局 | 空历史、游标追平、无需回放均可结束 |
| 直连失败后 relay 成功 | 一次操作的回退与最终结果，连接层证据单独标注 | 回退成功不算两次业务失败 |
| 提示有 ACK，但 Agent 没输出 | 区分排队、执行无输出、进程退出或终态不明 | 正常排队、长任务持续输出不误报 |
| 多会话/分屏同时打开，夹杂迟到回复 | 当前操作的阶段独立，旧回复不终结新尝试 | 取消/切电脑不污染当前操作、不重复创建会话 |

**B 完成时**：拿到诊断编号后，可还原已覆盖的新版本操作的最后成功阶段、失败或恢复过程；遇到旧版本、关闭采集或掉线缺报时明确显示证据边界，不猜测“内容太多”是根因。

## 4. 全程不变的边界

- Firebase Analytics 继续看整体趋势；Sentry 保存受控错误、阶段日志与手工性能信息。Sentry 采样事件数不当作真实用户数或总体失败率。
- 诊断数据由各组件独立 HTTPS 上报。relay 保持零知识，只关联连接，不接收业务正文或业务 trace；第三方 Agent CLI 的内部状态只在我们实际可观测的调用边界描述。
- 不上传 prompt、会话标题/正文、文件路径或内容、原始 stderr、账号/IP、密钥/token、配对材料和密文；新增字段、缓存、SDK 自动补充内容都检查最终上传结果。
- App 与 daemon 的采集授权独立。关闭后停止采集/待发上传，重开不补报关闭期间内容；已经送达后台的数据不承诺撤回。
- 继续在现有免费套餐与主方案预算内实现，不新增日志中转平台，不开启 Replay、全量控制台采集或逐 token 日志。原生 spans 的可用性和消耗用实际证据校准。

## 5. 完成标准与证据记录

每项统一记录：**待确认 → 待开发/补验 → 本地通过 → 实际包云端通过 → 验收完成**。已有入口和历史测试可复用；有新变更、失败或未解决风险时才扩大回归。

任务验收必须同时具备：

1. 适用故障分支的业务结果与诊断分类一致，最后成功阶段可解释。
2. 正常、取消、等待、恢复和混合版本对照没有错误归因、串会话或重试放大。
3. 真实上传内容和有关缓存通过敏感哨兵检查，诊断失败不阻塞业务。
4. 实际包、版本、环境、发生时间、诊断编号与后台定位方式可复查；未收到、迟到、被抑制和不适用分别记录。
5. 产品结果事件、对应视图和指标口径有独立验收：预期事件数量与正式可查询结果一致；DebugView 只能证明开发接收。无精确编号时记录候选关联；留存/版本判断分别记录数据窗口与覆盖，报表配置通过不代表已有产品结论。
