# 用户反馈排障与测试版本交付

用于“用户说没修好”“之前加的日志能不能定位”“补日志后给用户一个 TF 包”等任务。通知问题的具体字段另见[推送诊断指南](PUSH-DIAGNOSTICS.md)。本流程由排障 skill 推进，已有 CI 执行测试、构建和外测提交；不为每类反馈复制一套发布流水线。

## 先确定交付目标

沿用当前会话已经确定的版本、平台和范围，只澄清真正缺失的信息。截图、日志中的用户猜测作为待验证线索，历史任务的操作记录不构成新任务授权。

| 当前请求 | 应推进到的结果 |
| --- | --- |
| 排查原因、审查已有日志 | 给出已证实的失败阶段、证据和仍缺的信息；不自动发版 |
| 补日志或修复 | 改动与验证完成，说明哪些组件必须安装或部署才生效 |
| 给反馈用户发 TestFlight 排查 | 构建、上传、处理、外测组、测试说明和 Beta 审核提交；等待 Apple 时明确当前状态 |
| 明确仅构建、仅上传或内部测试 | 完成指定范围，不自动扩大成公开外测 |
| 正式上架或全平台发版 | 按明确指定的平台和发布方式进入[发布手册](../RELEASE.md) |

“准备给用户测试”的 TF 包不能在 `VALID` 就收尾。已提交 Beta 审核可报告“外测提交完成，等待 Apple”；只有审核与外测可用状态确认后，才能报告“用户可以安装”。内部测试与外部测试的完成标准分开核对。

## 1. 建立证据链

1. 核实用户实际安装的版本/build、各相关组件版本、故障时间与时区、复现动作、前后台及网络状态。先使用已有证据，不要求用户重复提供。
2. 对照最近修复提交、实际部署版本与当前源码。代码存在、测试通过、已安装、已部署分别记录。
3. 按业务链路定位最后一个有证据的成功点，以及其后的第一个失败或未知点。把“已证实”“推测”“缺证据”分开，避免用最终超时解释所有上游故障。
4. 查询正确组件的 Sentry 项目，同时查 Logs 和 Issues，检查 release、环境、时间窗口和诊断分享状态。再查本地诊断与服务日志；云端没有记录不能证明代码未执行。

推送实例：手机偏好 → 系统权限 → APNs token 回调 → relay 登记/数据库/ACK → daemon 通知意图 → relay 投递 → 系统展示设置/前台隐藏决定。`peer offline` 只说明连接状态，不能单独证明后台刷新权限是原因；relay 没有 token 也不能单独证明 Apple 从未回调 token。

只读访问与生产重启分开。daemon 更新遵守 [AGENTS.md](../../AGENTS.md) 的单实例及活跃会话规则；relay 部署使用当次授权和部署流程。不要为了取日志另外启动产品 daemon。

## 2. 审查并补齐关键日志

逐项核对生产者、承载层、最终出口，形成简短的覆盖表：

| 边界 | 必须能回答的问题 |
| --- | --- |
| 用户设置与系统能力 | 哪个开关、哪一层权限或能力阻止了继续执行？ |
| 原生/API 调用 | 是否发起、成功回调、失败回调，还是没有回调而超时？ |
| 网络与服务回执 | 未发送、写入连接、对端拒绝、数据库失败、ACK 超时分别是什么？ |
| 恢复与竞争 | 第几次尝试，是否耗尽、被新请求替代，是否最终确认或恢复？ |
| 用户可见结果 | 系统允许展示吗？App 是否主动隐藏？哪些最终效果根本没有可观测回调？ |
| 日志出口 | 只在本机、进入自有队列、发往 SDK，还是已有后台接收证据？ |

核心错误在发生边界记录，不能只在重试末尾统一报 `unavailable`。原生错误保留允许表中的 domain 和有界数值 code；不要上传任意异常描述、userInfo、token、稳定 token 哈希、账号/设备/会话标识、通知正文或路径。已有服务日志允许的身份前缀不自动扩展到云端。

需要复现的阶段事实应能避开成功 trace 的抽样，同时保留现有速率、预算和用户分享开关。利用有界、脱敏的本地复制记录补足离线/限流时的证据；明确它的保留期限、关闭后的清理及关联 ID 的范围。跨账号或跨组件关联不能超出真实提供的能力。

对当前推送实现，使用 `Diagnostics.push`，查 `EP-28` 的 stage/code、原生错误字段及随机 trace；事件清单和本地记录边界以[推送指南](PUSH-DIAGNOSTICS.md)为准。不要把 `stored`、APNs accepted 或“向系统返回 banner 选项”写成“用户看到了通知”。

## 3. 验证的是最终记录，不只是日志调用存在

- 测试真正会混淆的分支，例如 token 获取失败与登记 ACK 超时、系统关闭提醒与 App 前台隐藏。
- 验证字段穿过 Kotlin → Swift/JVM → Sentry **最终 envelope** 后仍存在，且私密字段已去除。验证限流/关闭下的本地记录行为。
- 运行受影响模块定向测试和对应平台编译。iOS 原生改动使用 `DiagnosticTests` 的隔离上传替身；真实 APNs 签发与受影响设备展示仍需用户复现。
- 对全量检查失败核实是否基线已有问题，保留证据；未跑完不能标绿。已通过的检查无需无理由重复。CI 的通过与真实用户问题已解决不是同一结论。
- 发布包检查生产 Sentry 配置、环境、release 和匹配的符号文件；本地 Debug 构建成功不能代替这些检查。

检查入口见[观测验证命令](README.md)、[发布配置](RELEASE.md)及[商店提审检查](../APP-STORE-REJECTIONS.md)。原始日志、测试报告和截图留在已忽略的 `_local/<task>/`；仓库只保存可复用说明与必要的脱敏证据。

## 4. 使用现有 CI 交付 TestFlight

先读 `.github/workflows/ios-release.yml`、`testflight-public-link.yml` 及其脚本；版本和发布命令以当前实现为准。`TF_VERSION`、`TF_REF`、run ID 均来自本次任务，不能沿用历史示例。记录本次期望提交 SHA，触发后核对 run 的 `headSha`，从 run number 确认 build 号。

### 新构建并交付给外部反馈用户

```bash
: "${TF_VERSION:?填入本次已确认版本}"
: "${TF_REF:?填入本次已验证提交所在的 branch 或 tag}"
bash scripts/check-release-version.sh "$TF_VERSION"
gh workflow run ios-release.yml --ref "$TF_REF" \
  -f testflight_only=true -f submit_for_review=false \
  -f automatic_release=false -f distribute_testflight=true
```

`testflight_only=true` 跳过正式商店元数据、版本绑定和 App Review；`distribute_testflight=true` 才会继续已有的外测工作流。两种审核不能混淆。版本源锁步不代表发布其他平台，常规 CI 的 Windows/daemon 检查也不是它们的发布任务。

### 已有处理完成的构建，只补外测

先确认目标版本和 build 的上传/处理证据，再运行：

```bash
gh workflow run testflight-public-link.yml --ref "$TF_REF" -f version="$TF_VERSION"
```

**当前脚本按版本选择最新 VALID 且未过期的 build，不接受指定 build 号。** 先核实目标就是该版本最新有效构建；如同版本存在更新构建、目标不明确，改用 ASC 精确选择目标，不要盲目派发。执行后必须从回执核对实际版本/build。

外测工作流复用既有测试组和链接、填写中英文 What to Test、关联构建、提交 Beta App Review 并读取 `externalBuildState`。需要沿用特定测试组时显式传 `group_name`，核对脚本实际选择及返回链接，不假设默认组总是正确。

上传已完成但外测失败时，只修复并重跑相应外测步骤；不要重新归档、消耗 build 号或触发其他端发版。遇到明确拒绝或不清楚的 API 状态，查看真实错误和当前状态后再处理，不能把工作流绿色当作 Apple 审核通过。

## 5. 按实际状态交付与回访

| 证据 | 可以报告的结果 | 仍需完成 |
| --- | --- | --- |
| archive/export 成功 | 已构建/上传 | Apple 构建处理及外测流程 |
| build 为 `VALID` | 构建处理完成 | 外测组、测试说明、Beta 审核提交 |
| 正确版本/build 已关联外测组，审核提交被接受 | 外测已提交 | 等待 Apple 审核结果 |
| `WAITING_FOR_BETA_REVIEW` 或审核中 | 等待审核/审核中 | 不能宣称新版已可安装 |
| 已确认审核通过且该 build 外测可用 | 新版可通过已核对链接安装 | 收集目标用户复现结果 |
| 用户在目标 build 复现并返回记录 | 可继续定位或验证修复 | 问题是否解决以证据和反馈判断 |

完成报告至少包含版本/build、实际审核状态、测试链接、已做验证、各组件安装/部署状态和待办。外部审核仍在等待时明确写出；没有建立后续监控，就不要承诺自动通知。用户明确要求跟踪时使用可用的定时/监控能力，只在状态变化或需要处理时通知。

给反馈用户的复现说明应短而可操作：安装指定 build → 检查相关开关/诊断分享 → 复现一次并记录时间与前后台状态 → 在本地记录失效前复制诊断。以当前包的真实 UI 为准。未被要求时只准备这段说明，不自行向外部用户发送消息。

用户回传后按同一版本、时间和 trace 检索；如果证据只定位了失败阶段，继续验证原因，不将“日志补好了”“测试包可安装”或“审核通过”当作问题已修复。后续正式发布、关闭 issue 和社区回访按该任务实际授权推进。

## 本流程防止的已发生遗漏

2026-09 的通知排障中，最初只有合并后的最终失败码，原生 token 错误与登记失败难以区分；补日志复核时又补出了系统展示设置和前台隐藏决定。TestFlight 曾停在 `VALID`，遗漏面向外部反馈用户的测试组和 Beta 审核提交。以上是本流程的维护依据，不是未来任务的授权或默认故障根因。
