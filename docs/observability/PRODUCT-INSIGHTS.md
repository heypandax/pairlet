# Pairlet 用户使用与问题分析方案

状态：**已纳入启动范围，A 批实施中**。日期：2026-09-10。

用户目标：一方面发现并解释实际使用中的问题，另一方面了解用户采用哪些能力、是否持续获得价值，以此决定产品开发优先级。本文选择首批分析视角，补充 [后续计划](FOLLOW-UP-PLAN.md)。用户已启动下一批；A 的公共维度、发送控制和事件字典正在实施，以下结果事件与报表仍待后续批次交付。

结论来自当前 App 流程、Telemetry/Diagnostics 代码和官方能力文档；本轮没有读取实际用户报表，下面的产品判断均是待数据验证的问题，不是已发现的用户行为结论。

## 1. 平台选择

**Firebase Analytics / 关联的 GA4 负责产品使用口径；Sentry 负责故障、耗时与技术原因。两边共享业务结果的定义，各自保留适合的数据。**

Firebase 已支持自定义行为事件和用户分群；详细漏斗、路径和留存分析在其关联的 GA4 中进行，Firebase 首页未必提供全部分析界面。这与我们已有埋点可以衔接。[Firebase Analytics](https://firebase.google.com/docs/analytics)、[GA4 漏斗](https://support.google.com/analytics/answer/9327974?hl=en)、[GA4 cohort 分析](https://support.google.com/analytics/answer/9670133?hl=en)。

Sentry 把结构化日志、错误栈和 trace 放在一起，更适合回答具体失败发生在哪一步、为何变慢、哪个版本引入异常。[Sentry Logs](https://sentry.io/product/logs/)、[Sentry Tracing](https://sentry.io/product/tracing/)。Sentry 也已有 Application Metrics，但本项目首批继续复用现有 Analytics 作为激活、使用和留存的统一口径，不为它们另建一套指标或新增 SDK 升级依赖。[官方功能说明](https://sentry.io/changelog/application-metrics-are-now-ga/)。

| 分析内容 | 主落点 | 另一侧的作用 |
|---|---|---|
| 新用户激活、漏斗流失、功能采用、留存 | Firebase / GA4 | Sentry 提供相应失败的技术样本 |
| 核心操作成功、失败、取消、恢复的总体趋势 | Firebase / GA4 的结果摘要 | Sentry 展开阶段、异常、耗时与版本 |
| daemon、relay 独立运行故障 | Sentry | App 看见的业务结果进入 Analytics；服务日志不重复算成用户操作 |
| 确切调用链、历史大小与处理瓶颈 | Sentry | GA4 保留耗时/规模分桶，便于判断受影响场景 |
| 原生自动崩溃 | 当前保留 Crashlytics，按既定条件验证后迁移 | 同一平台同一构建保持单一自动采集负责人，计数不相加 |

首批交付两处可用的分析入口及相同指标字典；不建设第三套仪表盘，不把 BigQuery、Firebase Performance 或付费分析功能设为前置。后续出现明确的明细关联或复杂统计需求，再评估导出与成本。

## 2. 选择五个重要视角

### 视角一：新用户能否顺利获得第一次价值

**要回答**：用户没有用起来，是没有完成电脑安装/配对，不清楚下一步，还是第一次打开/执行真的失败？

- 主漏斗：首次被观测 → 引导 → 配对尝试 → 配对成功 → 连接 ready → 第一次有效使用。不同配对入口分别观察；Demo、自有电脑、共享/协作入口分别建分支，不能强行套同一条必经路径。
- “第一次有效使用”要求用户主动发起，并实际看到历史/当前结果、收到真实 Agent 输出，或完成一项已被应用的审批。仅启动 App、配对、socket 建立或发送提示不满足这一口径。
- 指标：各阶段到达安装数、转化与退出位置、配对重试分布、首次有效使用耗时；Demo 到真实使用的转化单列。
- **Firebase / GA4 为主**：漏斗、入口与版本分层。**Sentry 辅助**：配对、连接、首次打开失败的固定原因和阶段。
- 支持的产品决策：优先改安装说明、配对入口、引导文案，还是连接与首次加载实现。用户没继续操作只能称流失/未继续，不能自动归因于技术错误。

### 视角二：用户想做的核心操作是否完成，等了多久

**要回答**：用户能否续接已有工作、发起任务、处理审批；“点了没反应”发生在哪个环节？

- 首批看三类操作：打开/续接会话、发送提示并收到响应、审批裁决被应用。查看历史也是有价值的使用，不要求每次进入 App 都发送提示。
- 区分打开意图、会话绑定、历史读取、接收/应用和实际布局；区分提示发送、ACK、首个真实输出与 turn 终态；区分审批点击、发送与实际应用。
- 指标：有结果样本的成功率、超时率、取消率、超时后恢复率；首屏、首个输出及审批应用耗时。将结果缺失和未知终态单列。
- **Firebase / GA4 看总体结果与场景分布；Sentry 查慢和失败的原因**，并保留同一次操作的阶段编号、安全栈和适量数值。
- 支持的产品决策：优先修历史处理、输入/排队状态、审批交互，还是某个 Agent 后端。收到首个输出只证明开始响应，turn 正常结束只证明协议完成，都不等于 AI 已正确解决用户问题。

### 视角三：离开再回来，工作能否继续

**要回答**：手机后台、电脑短暂离线、网络切换和重连后，用户能否恢复工作；哪些版本或后端持续影响可用性？

- 覆盖前后台恢复、直连转 relay、会话重订阅、daemon/Agent 意外结束和持续服务故障。
- 指标：恢复操作的结果、恢复耗时、恢复后再次失败、受影响的参与采集安装数；用户主动关闭与不可恢复断开分别统计。
- **Sentry 为技术主入口**：App/daemon 操作证据与 relay 连接证据分开呈现。**Firebase / GA4 留恢复结果和用户层面的影响摘要**。
- 支持的产品决策：连接恢复、历史续传、后台行为、错误提示和版本回归的修复优先级。直连失败后 relay 成功记回退恢复，不将它计为两次业务失败。

### 视角四：哪些工作流被发现、完成并重复使用

**要回答**：用户主要把 Pairlet 用作查看进展、继续对话、发起任务还是审批工具；某项能力用得少，是没看到、不会用、用不了，还是暂时不需要？

- 首批功能集合：续接/查看会话、发送新任务或继续提示、审批、文件查看、后台/定时任务。Agent 选择和新建/恢复类型作为固定维度，不采集任务内容。
- 指标：可用/曝光 → 尝试 → 完成 → 后续复用。曝光只在实际呈现且功能对当前平台/后端可用时记录，功能不可用的用户不进入采用率分母。
- **Firebase / GA4 为主**；失败尝试再到 Sentry 查原因。只记录关键工作流，不添加全页面点击流或所有按钮埋点。
- 支持的产品决策：首页入口、默认展示、功能引导和后端适配顺序。低采用率不能单独证明功能没有价值，需结合曝光、完成率及现有用户反馈。

### 视角五：用户是否持续获得价值，改版有没有改善

**要回答**：首次用成功的用户是否回来；体验过失败的群体是否更难回访；修复或改版后的变化是否值得继续投入？

- 建议主指标：**每周完成至少一次有效使用的参与采集 App 安装数**。有效使用必须由用户主动发起且达到视角一的结果，不计后台心跳、自动重连、仅收到推送或无人查看的自动任务完成。
- 留存以 `first_value_observed` 纳入群组、以 `value_reached` 判断返回，观察 D1、D7 和后续周；前者是持久标记后的首次观测，不代表新安装。这个远程伴侣产品也可能按需使用，所以周复用与日留存一起看，不以每日打开次数单独评价价值。
- 分析首次使用场景、平台、Agent、版本，以及遭遇/未遭遇核心失败的群组；同一观察窗比较后续有效使用。
- **Firebase / GA4 为主**；Sentry 用来解释版本差异和失败类型。
- 支持的产品决策：优先解决阻碍复用的问题，验证功能改进是否伴随更高完成率和复用。相关性不证明因果；版本覆盖、用户构成、样本量和观察窗不一致时不直接宣布改版有效。

GA4 cohort 依据设备数据分组。当前不新增账号标识或跨端身份拼接，因此手机与桌面端分别统计，不能相加为去重真人数；重装、采集关闭和首次观测不完整都会影响口径。[GA4 cohort 的身份边界](https://support.google.com/analytics/answer/9670133?hl=en)。

## 3. 现有代码可复用什么，先修正什么

已核查的公共入口是 [Telemetry.kt](../../mobile/composeApp/src/commonMain/kotlin/dev/ccpocket/app/telemetry/Telemetry.kt)，主要业务落点在 [PocketRepository.kt](../../mobile/composeApp/src/commonMain/kotlin/dev/ccpocket/app/data/PocketRepository.kt)。

| 当前事实 | 本次设计处理 |
|---|---|
| 已有 app_launch、onboarding、pair、connected、session_opened、prompt_sent、approval、help 事件 | 复用名称与原有口径；补结果，不全量重埋 |
| `session_opened` 在请求发出前记录 | 继续解释为打开意图；新增独立的最终结果和展示证据 |
| `prompt_sent` 在实际发送之前记录；`approval_decided` 在裁决发出前记录 | 作为尝试/用户决策，不冒充执行完成或 Agent 已应用 |
| 已有 demo=1 用于 Demo 分流，真实操作通常不带该值 | 新事件明确标识运行场景，旧事件按原语义兼容；验收检查所有相关分支，避免 Demo 混入真实激活 |
| 核心使用事件缺少完整结果、后端/场景维度和统一测试流量标记 | 先完成统一字典、结果来源、去重和内部流量隔离，再解释漏斗与留存 |
| desktop 使用独立随机 client_id，经 GA4 Measurement Protocol 上报，session_id 按进程生成，engagement_time_msec 固定为 100 | 先分平台验证实际报表；这个固定值不能用作真实使用时长，也不与移动端自动 session 时长比较 |

桌面端细节来自 [Telemetry.desktop.kt](../../mobile/composeApp/src/desktopMain/kotlin/dev/ccpocket/app/telemetry/Telemetry.desktop.kt)。Google 明确说明纯 Measurement Protocol 可能只有部分报表能力，因此桌面端的留存/漏斗须实测并标清缺口；不因为 HTTP 请求成功就认为标准报表完整可用。[Measurement Protocol 限制](https://developers.google.com/analytics/devguides/collection/protocol/ga4)、[事件校验](https://developers.google.com/analytics/devguides/collection/protocol/ga4/validating-events)。

## 4. 统一事件与两侧关联

新增名称为提案，确认后由事件字典冻结；下面均不表示当前代码已经实现。

| 行为 | Analytics 建议新增摘要 | Sentry 侧记录 |
|---|---|---|
| 会话打开 | `session_open_result`，区分成功、失败、超时、取消与未知；必要时独立 `session_open_recovered` | 同编号下的读取、编码、传输、应用/展示阶段和失败样本 |
| 提示执行 | `prompt_response_result`、`turn_result`，分别说明首次响应和本次 turn 终态 | ACK/排队/执行阶段、Agent 协议和退出证据 |
| 审批 | `approval_apply_result` | 呈现/裁决/发送/应用的安全分类；正常等待与拒绝不报内部错误 |
| 恢复 | `connection_recovery_result` | 直连回退、relay 连接关系、重订阅和恢复阶段 |
| 关键功能 | `feature_exposed`、`feature_used`，限定首批功能词表；完成结果复用对应业务结果 | 异常才关联诊断，不记录所有正常 UI 操作 |
| 有效使用 | `value_reached`，由确认的用户主动成功结果派生，每种动作不重复统计 | 不额外产生错误；可按已有诊断编号查当次证据 |

每次操作在业务状态层生成一份明确结果：Analytics 发低基数摘要；Diagnostics 决定采样、聚合或保留错误。Analytics 的结果摘要不沿用 Sentry 的成功日志 1% 采样；两者都遵守采集开关和自身上传能力。摘要不能由两个 SDK 的回调分别判断成功。

固定维度优先使用平台/版本、环境/内部流量、Demo/真实、入口、Agent、操作类型、阶段、结果、固定原因、耗时/规模分桶。模型名、工具名、动态错误类型先归一成有界词表；不把项目名、会话名、完整模型字符串当作报表维度。

`diag_event_id` / `diag_trace_id` 主要供 Sentry 查询。Analytics 仅在已验证的事件原始参数能力下保留可选编号，不注册高基数自定义维度，不承诺 Firebase 标准报表能逐条点击跳转。没有精确编号时，按同平台、版本、阶段和时间窗查询 Sentry，明确标为候选关联。relay 始终只有连接级证据。

## 5. 数据口径先于报表

1. **分母来自同一套业务结果。** 有结果样本成功率 = success / 已记录的有效结果样本；失败、超时、取消、未知分别展示。要报告整批尝试的完成率，必须先确认同一尝试群组和观察窗的结果覆盖，不能简单用同一小时的结束数除以开始数。
2. **迟到与缺失单列。** 超时后恢复不覆盖最初的超时事实；同一操作只产生一次主结果。App 强杀或关闭采集导致没有结果时，不自动算成功；窗口边界尚未完成的任务也不自动算失败。
3. **用户数与事件数分开。** 操作数、受影响的参与采集安装数、Sentry 接收样本数分别命名。Sentry 采样/限频错误数不能除以所有 Analytics 操作数得到故障率。
4. **内部、Demo 和正式使用分开。** 真机调试、自动测试、独立 smoke、后台服务日志不混入正式用户激活与留存；旧版本缺少标记的记录保留未知，不追溯伪造分类。
5. **新版本只统计支持该口径的覆盖范围。** 旧端未上报历史完成、审批应用或 feature exposure 时注明覆盖限制；不能认为没有事件就没有使用，也不把上线新埋点后的增长直接称为用户增长。
6. **“首次”是可观测范围内的首次。** 已有安装第一次出现新事件不等于新用户；无法识别既往使用时标为首次观测。D7/周留存只比较已达到完整观察期的群组；样本少时显示人数和区间，不依靠一个百分比作大决策。

## 6. 首批实施与验收

首批主线选择 **视角一、二、三**；同时为视角四、五保留少量固定维度与 `value_reached` 结果，之后用真实积累数据验证复用。已有 OBS-01–10 / EP-01–30 继续作为技术任务，不另建一套重复日志系统。

| 交付批次 | 对应后续计划 | 产品与技术一同交付的内容 |
|---|---|---|
| 口径与必要基础 | A 的必要部分，OBS-01 / OBS-10 | 当前事件审计、内部/Demo 隔离、事件字典、去重、开关/脱敏、实际平台报表边界；校验 desktop MP |
| 首次价值与会话完成 | B，OBS-02 / OBS-03 | 激活漏斗、session_open_result、首屏结果与耗时、跨端故障诊断；“部分会话打不开”可现场复现并解释 |
| 执行与连续使用 | B 及 C 的审批/生命周期项，OBS-04 / OBS-05 / OBS-06 | 提示首响应/turn、审批应用、恢复结果和有效使用；对应后台阶段与正常对照 |
| 采用、复用与版本评估 | C / D，OBS-06–10 | 首批五功能的采用路径、按平台/版本的有效使用群组、成熟观察窗的复用分析；其余错误路径继续覆盖 |

五组件全部符号与完整缓存实验仍在范围内，但除开关/脱敏/不阻塞业务/必要预算外，独立补验可与业务主线交错推进；不必等待全部平台验收结束才开始会话闭环。

每批验证一个明确的用户旅程，记录预期 Analytics 摘要数量、Sentry 事件分类和实际后台回执；同时验证成功、失败、取消、重试、后台、重复回复、Demo、内部流量和关闭采集。Firebase DebugView 用于开发核对，正式漏斗/留存另在可查询数据就绪后验证；不把调试可见当成正式报表已完成。[Firebase DebugView](https://firebase.google.com/docs/analytics/debugview)。

开发产物包括：`EVENT-CATALOG.md`（事件与指标字典）、GA4 的激活/结果/采用/复用视图、Sentry 的阶段/版本/服务故障查询，以及使用同一构造场景的两侧回执索引。实际入口和查询写入 `queries.md`，回执写入 `ACCEPTANCE.md`，首轮有明确数据窗口和覆盖范围的产品观察写入 `PRODUCT-REVIEW.md`。这些产物已统一列入后续计划；视图实际创建与权限/套餐可用性通过后才标完成，真实样本不足的判断保留待观察，当前只是设计。

## 7. 如何用数据决定下一步

日常先看核心操作失败与版本回归；按成熟观察窗回顾激活、功能采用和复用。每个待开发改进写清：观察事实 → 假设 → 受影响范围 → 改动 → 同口径验证。本文不创建自动巡检或通知任务。

例如，若“配对成功但首次有效使用低”，先按 GA4 漏斗确认掉在哪一阶段，再用 Sentry 判断是历史读取失败、连接恢复失败，还是没有技术失败证据；分别对应修实现或改善引导。若某功能曝光很低而已尝试用户完成/复用较好，优先评估入口；若曝光充分但完成率低，先解决可用性。没有日志支持的动机问题再结合现有反馈或经授权的用户研究，不推断用户在做什么私密任务。

隐私继续沿用主方案：不记录会话正文、prompt、标题、文件路径/内容、账号、IP、令牌或密钥；使用受控操作分类与去标识化的安装级统计，尊重现有采集关闭状态。daemon/relay 独立服务上报不用于重建用户身份。
