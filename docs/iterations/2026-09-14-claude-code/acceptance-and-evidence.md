## 1. #362 项目置顶的实际验收

需求：[Issue #362](https://github.com/heypandax/pairlet/issues/362)。项目同步代码 `859bcaf4` 已在 main，不重新实现。会话置顶和手机新的会话置顶入口没有本轮产品决定，不自行扩展。

准备两端都连接同一台测试电脑的 owner 配对；另准备第二台已配对电脑用于身份隔离。仅使用可恢复的测试项目置顶，先记录原列表，不删除真实配对或重置用户存储。

| 场景 | 通过条件 |
|---|---|
| A 端置顶／取消／排序 | B 端收到同一电脑的变化，已有入口仍正常 |
| A/B 离线分别改不同项目 | 重连后不同项目操作都保留，最终顺序符合协议 |
| 同一项目并发相反操作 | 按 daemon 接收规则收敛，双方看到一致的最终状态 |
| 切电脑、同路径不同电脑 | 清单和未确认操作不串电脑 |
| 重启客户端与 daemon | 已确认状态保留，未确认操作按现有恢复策略显示 |
| 旧快照／ACK 晚到、撤销权限 | 不复活取消项，不在失效授权下继续发送 |
| 新旧端组合 | 没有新 capability 的端保持旧能力，不能误发送新消息 |

重配对／存储重建／物理断电另用隔离数据和得到允许的测试设备。旧绑定未确认操作本来就应保留为待处理状态，不能为了让测试看起来同步成功而静默重放到新身份。发现失败后由 Claude Code 给出准确帧序列、归属和最小修复；未执行的故障场景明确列出。

## 3. #347 ChatGPT 接管可见性

[Issue #347](https://github.com/heypandax/pairlet/issues/347) 已发布原生名称标记“CC Pocket · 原名”；剩余是无需重启即可发现与受支持的直接定位。当前没有证明 ChatGPT 的刷新／打开机制可由 Pairlet 控制。

Claude Code 的有界调查：

1. 核验安装的 ChatGPT、Codex CLI 和 Pairlet 版本；沿当前接管路径识别“原会话、接管结果、是否真的 fork”与原生名称写入。
2. 在隔离项目中观察不重启 ChatGPT 时能否出现；分别尝试其正常导航／搜索／刷新路径，记录哪一步使会话可见。保护真实工作会话与单写约束。
3. 查本机受支持接口和当前官方文档。只有确实存在并实测有效的 URI／命令／打开入口，才设计客户端动作；不猜 `chatgpt://...` 路径，不直接改第三方数据库，不把强制重启包装成修复。
4. 若只有外部 App 重启能刷新，明确归属与缺少的受支持接口。可提供清楚的会话名称／定位说明，但不要把更多前缀或重复命名当作解决刷新问题。

有受支持打开方式后，单独形成小实现：目标 ID 与原会话关联、仅打开正确目标、失败反馈和旧 App 降级；不调整 #316 的写占用或强制 takeover。没有决定性证据就交付调查结论，不先改 backend。
