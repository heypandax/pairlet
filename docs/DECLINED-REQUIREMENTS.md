## D1：首启页「把安装链接发到电脑」与演示结束的下一步

**需求**：新用户在手机上看到安装命令，却要到电脑上执行。设想在首启页加一个入口，把安装方法发到用户自己的电脑；并在演示结束后给出明确的下一步，引导去正式设置。

**来源**：[#342](https://github.com/heypandax/pairlet/issues/342) 2026-10-03 的回看结论里提出的两个方向。

**做过的事**

- 重读了接入观测后的激活数据。
- 出了一轮设计稿并做了交互评审，见[设计说明](design/claude-design-handoff/first-run-send-to-computer-v1/README.md)。

**为什么不做**

- **证据不足。** 所依据的海外与国内差异，受应用审核安装、无法识别地区的安装和小样本影响，剔除这些因素后不足以支撑「用户卡在换到电脑这一步」。「很多用户当时不在电脑旁」是写设计 brief 时加的假设，没有任何用户反馈支持；Issue 记录里也没有人提过这个困难。
- **即使假设成立，涉及的用户量也很小**，在当前安装量下很长时间都测不出效果。
- **顺序反了。** 原定先把观测埋点发出去、回收数据后再判断方向；埋点还没随版本发布，设计就先做了。
- **设计本身的问题。** 「发到电脑」不是首启的主路径，设计稿却让它占了主按钮，把安装命令和配对入口降为次级，还在演示的消息流里插入卡片。

**保留的部分**：#342 作为问题本身仍然开着。为它补的三处观测埋点已在代码里，随版本发出后用于重新判断。

**重启条件**：埋点发出并积累数周数据、排除审核安装后，仍能看出用户停在「去电脑安装」这一步；或者有多名真实用户明确反馈这一步的困难。重启时辅助入口只能作为安装命令旁的次级动作，首启页的主路径（安装、配对）保持不变。

## D2：朗读

**需求**：在文件查看器里朗读 Markdown 文档。试用后扩展为：离开界面继续读、可调倍率，并做成对回复、子代理报告、语音备忘等其他文本也适用的通用播放器。

**来源**：维护者自己的想法（2026-09-30），试用 iOS 试做版后提出扩展。

**做过的事**

- iOS 上用系统语音试做过文档朗读。代码没有提交，撤回需求时已从工作区移除。
- 为通用播放器出了一轮设计稿并做了交互评审，见[设计说明](design/claude-design-handoff/read-aloud-v1/README.md)。
- 核对了 Issue 记录和功能使用情况。

**为什么不做**

- **只有单一来源。** Issue 记录里没有任何用户提出过朗读或语音播报。
- **受众有限。** 文档朗读的入口在文件查看器里，而文件查看器只是一部分用户在用，使用频次远低于发消息。
- **设计本身的问题。** 朗读不是聊天的主路径，设计稿却把播放条放在输入区上方，并在每条回复上常驻入口；有提问卡时还会进一步挤压正文。
- **通用化的代价不小。** 锁屏和后台继续朗读需要申请音频后台权限并在审核备注里说明，各平台的语音引擎也要分别适配。
- **使用场景没有说清。** 是锁屏放在口袋里听，还是人在桌前听，决定了要投入多少，这一点当时没有答案。

**重启条件**：有多名用户提出；或者维护者明确了固定的使用场景，并愿意先用最小的版本自用验证。重启时入口不占输入区上方，也不在每条消息上常驻。
