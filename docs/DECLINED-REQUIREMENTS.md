维护日期：2026-10-05。

## D1：首启页「把安装链接发到电脑」与演示结束的下一步

**需求**：新用户在手机上看到安装命令，却要到电脑上执行。设想在首启页加一个入口，把安装方法发到用户自己的电脑；并在演示结束后给出明确的下一步，引导去正式设置。

**来源**：[#342](https://github.com/heypandax/pairlet/issues/342) 2026-10-03 的回看结论里提出的两个方向。

**做过的事**

- 重读了接入观测后的激活数据。
- 出了一轮设计稿并做了交互评审，见[设计说明](design/claude-design-handoff/first-run-send-to-computer-v1/README.md)。

**为什么不做**

- **证据不足。** 所依据的海外与国内差异，受应用审核安装、无法识别地区的安装和小样本影响，剔除这些因素后不足以支撑「用户卡在换到电脑这一步」。「很多用户当时不在电脑旁」是写设计 brief 时加的假设，没有任何用户反馈支持；Issue 记录里也没有人提过这个困难。
- **即使假设成立，涉及的用户量也很小**，在当前安装量下很长时间都测不出效果。
- **顺序反了。** 原定先把观测埋点发出去、回收数据后再判断方向；埋点还没随版本发布，设计就先做了。
- **设计本身的问题。** 「发到电脑」不是首启的主路径，设计稿却让它占了主按钮，把安装命令和配对入口降为次级，还在演示的消息流里插入卡片。

**保留的部分**：#342 作为问题本身仍然开着。为它补的三处观测埋点已在代码里，随版本发出后用于重新判断。

**重启条件**：埋点发出并积累数周数据、排除审核安装后，仍能看出用户停在「去电脑安装」这一步；或者有多名真实用户明确反馈这一步的困难。重启时辅助入口只能作为安装命令旁的次级动作，首启页的主路径（安装、配对）保持不变。

## D2：朗读

**需求**：在文件查看器里朗读 Markdown 文档。试用后扩展为：离开界面继续读、可调倍率，并做成对回复、子代理报告、语音备忘等其他文本也适用的通用播放器。

**来源**：维护者自己的想法（2026-09-30），试用 iOS 试做版后提出扩展。

**做过的事**

- iOS 上用系统语音试做过文档朗读。代码没有提交，撤回需求时已从工作区移除。
- 为通用播放器出了一轮设计稿并做了交互评审，见[设计说明](design/claude-design-handoff/read-aloud-v1/README.md)。
- 核对了 Issue 记录和功能使用情况。

**为什么不做**

- **只有单一来源。** Issue 记录里没有任何用户提出过朗读或语音播报。
- **受众有限。** 文档朗读的入口在文件查看器里，而文件查看器只是一部分用户在用，使用频次远低于发消息。
- **设计本身的问题。** 朗读不是聊天的主路径，设计稿却把播放条放在输入区上方，并在每条回复上常驻入口；有提问卡时还会进一步挤压正文。
- **通用化的代价不小。** 锁屏和后台继续朗读需要申请音频后台权限并在审核备注里说明，各平台的语音引擎也要分别适配。
- **使用场景没有说清。** 是锁屏放在口袋里听，还是人在桌前听，决定了要投入多少，这一点当时没有答案。

**重启条件**：有多名用户提出；或者维护者明确了固定的使用场景，并愿意先用最小的版本自用验证。重启时入口不占输入区上方，也不在每条消息上常驻。

## D3：评审请求，以及会话交接与协作联系人

**需求**：两项协作能力，共用同一套协作联系人与凭据，因此一起下线。

- **评审请求（ReviewRequest）**：把一个评审任务连同说明和产物交给同事，对方用自己电脑上的 Agent 完成评审后回传结构化结果。配套 `pairlet review`、`pairlet collaborator` 命令和随仓库分发的 `review-request` skill。
- **会话交接（Session Handoff）与协作联系人（Collaborator Link）**：把正在进行的会话临时交给同事驱动，结束后归还；为此在双方之间建立长期的协作联系人。

**来源**：维护者自己的想法。会话交接首次提交于 2026-08-02，评审请求首次提交于 2026-08-05。Issue 记录里没有用户提出过这两项需求；与之相关的只有一条经维护者转录的缺陷反馈 [#251](https://github.com/heypandax/pairlet/issues/251)（桌面端打开「协作联系人」后报错并卡死）。[#232](https://github.com/heypandax/pairlet/issues/232) 说的是同一会话里多个 Agent 之间分工交接，与本案无关。

**做过的事**

- 完整实现并随版本发布：daemon 侧的交接状态机、协作者凭据与授权、对端收件箱、本地控制接口与 CLI、打包的 skill；手机与桌面的发起、接收、归还界面；接收方提醒推送。
- 设计与复审见 [评审请求设计](design/REVIEW-REQUEST.md)、[会话交接设计](design/SESSION-HANDOFF.md)、[交接实现复审](design/SESSION-HANDOFF-IMPLEMENTATION-REVIEW.md)，界面设计见 [session-handoff](design/claude-design-handoff/session-handoff/README.md) 与 [session-handoff-contacts](design/claude-design-handoff/session-handoff-contacts/README.md)；当时的使用说明归档在 [协作接力使用说明](archive/COLLABORATION-HANDOFF.md)。
- 2026-10-05 从产品中删除。

**为什么下线**

- **没有用户需求来源。** 两项都出自维护者的设想，没有用户提出过。
- **对主路径侵入大。** 请求路由在发送、审批、取消、回退上加了交接驱动门；会话注册表为交接加了热转冷重建与回收保护；入站门多了一种凭据分支；App 的连接状态里多了收件箱模式，输入区也要按交接状态门控。主路径上每改一处，都要同时考虑交接。
- **始终没有完成验收。** 使用说明里一直标着「双机实网验收尚未完成」，没有走到可以对外推荐的状态。
- **安全面。** 协作者是一种可以连入的长期凭据，还要常驻一条对端 relay 连接；围绕它出过把协作者密钥误写成完整设备的缺陷（[#207](https://github.com/heypandax/pairlet/issues/207)）。

**保留的部分**

- 协议里的消息类型全部保留。旧版 App 或旧版 daemon 发来这类请求，会得到「不支持」或空列表；旧的邀请链接（`ccpocket://review-contact`、`collab`、`handoff`）在新版 App 里提示「该功能已下线」。
- `pairlet review`、`pairlet collaborator` 保留为隐藏命令，只提示已下线。
- 存量协作者凭据在 daemon 升级后失效：入站拒绝，并通知 relay 吊销。磁盘上不含密钥的历史状态文件不自动删除。
- 对端传输、链接存储、原子写文件和本地控制门被远程执行（[#367](https://github.com/heypandax/pairlet/issues/367)，`pairlet agent`）复用，已搬到中性的包里继续使用；relay 的协作者票据标记也被远程执行复用，保留不动。`CredentialKind.COLLABORATOR` 等枚举值为凭据失效与数据解码保留。

**重启条件**：有多名真实用户（不是维护者）明确提出「把会话或评审交给同事」，或者团队协作成为产品方向。重启时不在主路径（发送、审批、会话打开、重连）上加门控；协作者凭据要有 relay 侧可确认的吊销路径；先做最小版本，在两台机器的真实网络上自用验证。

## D4：文件夹共享（访客）

**需求**：主人把电脑上的一个文件夹分享给别人；对方用一次性邀请以访客身份加入，只能在这个文件夹范围内开会话、跑 Agent，到期或撤销后失效。配套 `pairlet share` 命令。

**来源**：[#115](https://github.com/heypandax/pairlet/issues/115)，由维护者在 2026-07-11 提出。Issue 记录里没有查到其他用户提出过这项需求。

**做过的事**

- 完整实现并随版本发布：daemon 侧的访客凭据、入站白名单与守卫、路径围栏、权限档位钳制、到期清理和 `pairlet share` 命令；手机与桌面的共享、加入界面；邀请链接。
- 界面设计见 [folder-share](design/claude-design-handoff/folder-share/README.md)。
- 商店与官网的宣传文案在此之前已经撤下，只为已在使用的用户保留了不进索引的手册页。2026-10-05 功能删除时，手册页一并删除。

**为什么下线**

- **承诺的边界守不住。** 访客自己批准访客会话里的权限请求。路径围栏只能覆盖能静态解析出目标路径的文件工具，shell 命令的读写目标无法静态确定，访客可以批准一条不受路径约束的命令，它以主人的系统用户身份运行。「对方不能访问其他文件夹」在技术上挡不住，只能靠「只分享给信任的人」兜底，与功能本身的承诺矛盾。
- **对主路径侵入大。** 请求路由的每个请求都带着访客范围做判断，客户端也有多处访客分支；每加一种新请求，都要为访客单独决定是否放行。
- **多一种可连入的长期凭据。**

**保留的部分**

- 协议里的消息类型与 `CredentialKind.GUEST` 枚举值，用于兼容旧端与让存量凭据失效。旧的邀请链接（`ccpocket://share`）在新版 App 里提示「该功能已下线」；`pairlet share` 保留为隐藏命令，只提示已下线。
- 存量访客凭据在 daemon 升级后失效：入站拒绝，并通知 relay 吊销。磁盘上不含密钥的历史状态文件不自动删除。
- 路径范围、档位钳制与会话路径限制的代码保留，桥接与远程执行仍在使用。

**重启条件**：有多名真实用户明确提出「把一个目录交给别人在我的电脑上用 Agent」；并且访客会话里的命令审批由主人来批，或者命令本身受路径约束（例如系统级沙箱、容器或独立系统用户），边界可以验证。重启时不复用「访客自己批准命令」的模型，也不在主路径上为访客加判断。

## D5：明文局域网模式

**需求**：手机在同一局域网里直接连电脑上的 daemon，不经过 relay。daemon 用 `run --local`（配合 `--host`）开一个明文 WebSocket 监听；App 配对页有「高级：直连局域网」入口，手动填地址连接；开发工具 `test-client` 也有对应的 direct 模式。

**来源**：项目最早期的调试脚手架，不是用户需求。2026-06-30 有两条经维护者转录的用户反馈（[#22](https://github.com/heypandax/pairlet/issues/22)、[#24](https://github.com/heypandax/pairlet/issues/24)）是在局域网连接下提的，当时局域网连接只有这一种方式；两条都是使用中遇到的问题，不是对这个模式本身的需求。

**做过的事**

- 从第一版起就有明文监听与 App 的手动直连入口。
- 2026-07-04 起加入加密的局域网直连（`--direct-bind`）：已配对设备在同一网络下自动绕过 relay，连接经过握手、认证与加密。
- 2026-10-05 删除明文模式的 daemon 入口、App 入口与 `test-client` 的 direct 模式。

**为什么下线**

- **没有握手、认证与加密。** 局域网里任何能连到端口的人都能驱动这台电脑上的 Agent。
- **原本的用途已有替代。** 「局域网更快」已由加密直连承担；调试与开发也已改用 relay 配对流程。

**保留的部分**

- 加密的局域网直连（`--direct-bind`）是保留的产品能力，不受影响。
- `run --local` 保留为隐藏参数，使用时说明该模式已删除并拒绝启动；`--host` 只对明文模式生效，现在会被忽略并给出提示。
- 明文直连从未在 App 里持久化，升级后没有需要迁移的数据；用过它的用户打开 App 时看到的就是配对页。

**重启条件**：如果要做「完全不经云端」的离线模式，需要一套不经 relay 的带认证配对（例如二维码携带 daemon 公钥与本机生成的秘密），连接走与加密直连相同的握手与加密。不能恢复无认证的明文监听。

## 新案例的录入规则

需求经过调研、设计或试做后决定不做时，在本文追加一条，不在别处复制完整案例。每条至少写清：需求是什么、从哪来、做过哪些调研或试做、为什么不做、重启条件、相关资料的链接。不写用户行为数据与比例。

同一个想法再被提起时，先读对应案例，确认重启条件是否已经满足。
