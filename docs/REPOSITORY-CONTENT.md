# 仓库内容与归档规则

Git 保存协作开发、构建、发布和维护所需的材料。原始工作过程先留本地，整理成可复用说明后再提交。文档入口见 [README](README.md)，共享 Agent 规则维护在 [AGENTS.md](../AGENTS.md)。

## 内容放在哪里

|---|---|---|

| 使用说明、接口契约、维护指南、已整理的设计决定 | 保留并维护，说明当前与历史状态 | `docs/`、`support/`、设计 handoff 中的 Markdown |
| 网站 / 商店素材生成脚本 | 保留，确保新 clone 能复现所需资产 | `marketing/site/`、`marketing/appstore/`、`marketing/preview/` |
| 发布或网站直接使用的定稿媒体、图标源 | 保留；修改时运行相应内容校验 | `fastlane/screenshots/`、`fastlane/previews/`、`site/assets/`、`assets/brand/` |
| 有必要追溯的、已脱敏的历史计划和验收 | 移入 `docs/archive/`，保留日期、版本、限制与双向引用 | `docs/archive/observability-2026-09/` |
| Claude Design 整包导出、HTML/JSX 原型、重复截图、缩略图、原始对话 | 放仓库外归档；本地保留副本时必须被忽略。只提交整理后的设计说明与来源链接 | 原 `docs/design/claude-design-handoff/` 的非 Markdown 内容及 `chats/` |
| 某次营销活动的分镜、供应商探针、生成回执和候选素材 | 本地或外部项目归档；需要成为公共工具时，先去掉活动和账号依赖并补使用入口 | `marketing/video/` 不再跟踪 |
| 运行日志、浏览器响应、原始分析数据、临时截图、会话交接 | 放仓库外或已忽略的 `_local/<task>/`；摘要先脱敏再提交 | 不进入 `docs/archive/` 充当原始数据存储 |
| 私钥、token、真实本机配置、IDE / Agent 状态、构建缓存和安装包 | 忽略；凭据使用本机配置或 CI Secrets，发行包通过 Release 分发 | `.env`、`.agents/`、`.claude/`、`build/` 等 |

生成文件不一定都要删除：`site/manual/` 是可部署手册，商店媒体是现有 CI 的上传输入，图标是构建输入。是否保留取决于实际消费者、可复现来源与维护成本。

## 清理方法

1. 先查看 `git status --short`、`git ls-files` 和引用，区分已提交文件、本地修改与已忽略资料。不要把“旧”直接等同于“无用”。
2. 对将要移出跟踪的原件做仓库外备份，记录源提交、相对路径与 SHA-256，并回读校验。已有未提交修改单独保存。
3. 对需要保留的历史文档使用迁移并同步引用；对本地工作材料使用 `git rm --cached -- <已核对路径>`，保留工作区原件并设置忽略规则。不要用 `git clean` 做批量整理。
4. 从待提交内容导出一个不含本地忽略文件的目录，再运行相关静态检查，避免本机残留原件掩盖缺失依赖。
5. 提交后，旧文件仍存在于 Git 历史。停止跟踪不会缩小既有历史或撤回已公开内容；若确认曾提交真实凭据，应先处理凭据，再单独评估历史清理，不能把本次整理当作已消除历史泄漏。

历史文档不是任务指令。原任务的“已授权”“暂不测试”“下一步”“待提交”只记录当时的决定；不能据此推断当前授权或完成状态。新增运行回执应先留本地，再把必要的脱敏结论更新到对应维护文档。

## 提交检查

```bash
# 暂存准备提交的修改后运行；检查 Git index，不读取凭据内容
python3 scripts/check-repository-content.py
git diff --cached --check
```

CI 执行同一检查，拒绝已跟踪但匹配仓库 `.gitignore` 的文件、明确属于本地的设计/会话/活动资料，以及未登记的单个大于 10 MiB 文件。个人全局 ignore 不影响仓库规则。现有两段 App Store 预览属于明确保留的发布输入，其尺寸/编码由 `check-appstore-content.py` 校验。

这个检查负责内容边界和体积，不代替凭据扫描、隐私审阅或资产授权确认。不要用 `git add -f` 绕过；如新增公共工具或必需大文件，先整理用途、依赖和验证方法，再有针对性地更新规则。
