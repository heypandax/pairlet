# Issue #347：Codex 接管后的桌面可见性与识别

日期：2026-09-05。状态：方案分析及隔离接口验证完成，尚未实施产品改动。

需求：[Issue #347](https://github.com/heypandax/cc-pocket/issues/347)。源码基线：`4a90933a99170c462a48bda36225b1e12001b439`。

## 结论

推荐采用「接管分支写入 Codex 原生名称＋在电脑的 ChatGPT 中直接打开对应会话」。名称解决同名难辨，按会话 ID 打开解决依赖侧栏查找的问题。ChatGPT 侧栏自动发现外部变化需要单独验收，不能把原生改名成功当作侧栏已经刷新。

当前证据支持两个独立缺口：

| 现象 | 已核验事实 | 结论强度 |
| --- | --- | --- |
| 接管后与原会话同名 | cc-pocket 在外部持有会话时调用原生 `thread/fork`；隔离实测分支继承原名；随后没有原生改名步骤 | 已确认机制与代码缺口 |
| 重启后才找到 | 本机存在 Codex 存储中已登记、桌面目录未收录的会话；独立 app-server 之间没有在探针观察窗口内传播创建、改名通知；重新查询即可读到新分支 | 桌面目录未及时同步是强证据支持的解释；尚未对用户指定样本做完整 UI 复现 |

## 证据

- `SessionRegistry.kt:543`：仅在接管且外部持有或持有状态无法确认时决定保护性分支；普通接续保留会话 ID。保持这条单写保护。
- `CodexBackend.kt:270`：接管分支走 `thread/fork`。`onThreadReady` 目前只处理 ID、运行参数、待发输入与 `SessionInit`，没有设置原生名称。
- `AgentBackend.kt:69`：默认不支持改名；`CodexBackend` 没有覆盖它。`SessionRegistry.kt:1089` 的空闲改名路径仍明确拒绝 Codex。
- `CodexTranscriptScanner.kt:119`：cc-pocket 从 Codex 的 `session_index.jsonl` 读取原生标题。隔离实测 `thread/name/set` 会更新该索引，因此已有标题读取链可以复用。
- `Conversation.kt:1700`：分支后继承 cc-pocket 分组；`RewindLineage` 明确只记录用户主动 rewind／fork，不记录接管分支。不能直接复用其折叠原会话的语义。
- 官方 [Codex App Server 文档](https://learn.chatgpt.com/docs/app-server) 提供 `thread/fork`、`thread/name/set`、`thread/list`、`thread/read`；`thread/name/set` 支持已加载会话或持久化历史，并产生 `thread/name/updated` 通知。

## 推荐实现

### 1．给真正的接管分支设置原生名称

- 条件同时满足「用户执行接管」和「返回的新会话 ID 与原 ID 不同」时，写入名称，例如 `CC Pocket · 原会话名`；同一原会话有多条接管分支时，加入接管时间以区分。
- `CC Pocket` 表达来源，不用会过期的「接管中」作为永久名称。只处理新分支；原地接续、再次打开、用户后来手动改名都不重复覆盖。
- 基于 `thread/fork` 返回的原生名称，必要时回退到已知原会话标题；通过 `thread/name/set` 写回，而非只改变 cc-pocket 的显示文本。
- 请求与回包放进现有握手状态机，按进程代次与会话 ID 去重。不得在解析回调中等待必须由该回调处理的后续响应；改名失败或超时必须有界，不能吞掉首条输入、无限等待或延迟 writer 交还。
- 接管来源与原会话关联按独立语义保存；不借用 rewind 的替换／折叠规则。

### 2．提供「在电脑的 ChatGPT 中打开」

- 使用已经确认的目标会话 ID 构造原生链接，提供明确的打开入口，用户无需先在同名列表中寻找。
- 首版覆盖本次 macOS 场景。手机按钮须由对应电脑的 daemon 执行本机打开；在手机直接打开 `codex://` 不等于打开电脑里的应用。桌面 cc-pocket 可走同一受控动作。
- 打开动作先确认当前回合已结束并完成已有的 writer 交还；正在执行时说明需等待，不自动中断回合。无输入的接管也需覆盖空闲占用释放。
- 仅允许机主对目标机器上的已知 Codex 会话执行，服务端自行构造固定 scheme 的链接，不接受任意 URL 或 shell 命令。没有目标应用或能力不支持时准确反馈。
- 回执区分「已发起打开」与「界面已展示」。接管时不自动弹出或抢占电脑前台。

### 3．单独验证桌面目录刷新

- 验证原生链接能否打开尚未进入桌面目录的会话，以及打开后是否补入侧栏。这是方案实施前的关键技术验证点。
- 若当前宿主提供可支持的刷新入口，再将其纳入打开流程；否则保留按 ID 直达，将「侧栏无需操作便自动出现」作为上游刷新能力问题跟踪。
- 不通过改时间戳、伪造用户消息、直接写桌面目录、重启应用或放宽单写保护来促使条目出现。重新查询 daemon 自己的列表，也不能代替 ChatGPT 刷新。

## 改动范围与验收

主要范围为 daemon 的接管命名和打开动作，以及 App 的入口与反馈。若需要增加手机到 daemon 的消息或能力字段，采用兼容扩展，并执行 protocol 兼容评审；机主权限、目标会话校验与本机打开动作需要安全评审。relay 无需承担桌面目录刷新。

实施顺序：先验证「未入目录的会话按链接打开」；通过后实现原生命名及打开闭环。接口能力已验证，完整用户路径尚未验收。

- ChatGPT 保持运行，接管一条它仍持有的会话：得到明确的新条目名；原会话名称及历史不变。
- 从手机选择「在电脑的 ChatGPT 中打开」：无需重启，准确到达接管后的 ID，能看到后续内容并安全继续。
- 原地接续不产生分支、不被重复添加名称前缀；重复打开或用户改名不被覆盖。
- 活跃回合、接管后未发消息、进程重连、重复通知、改名失败和旧版本能力缺失都有明确结果。
- 名称写入、索引可读、链接可打开、侧栏自动刷新分别记录结果；自动刷新未通过时，不以其他三项成功宣称该项完成。
